# 배포

> 원본 [docs/deploy.md](../../../docs/deploy.md)(AIHOT, 중국어, 커밋 b868d38)의 한국어 번역입니다. 한국어판에서 바뀌는 부분은 [README.ko.md](../../../README.ko.md)를 보세요.

## Docker 사용(권장)

Docker(Compose 포함)가 설치된 머신이 필요합니다. 클라우드 서버는 최소 2코어, 4 GB 메모리를 권장합니다. 이미지를 빌드할 때 필요합니다.

```bash
git clone https://github.com/KKKKhazix/AIHOT.git myhot
cd myhot
node scripts/init-env.ts --llm-key <모델 API 키>
```

`init-env.ts` 는 `.env` 를 만들고, 무작위 키와 관리자 비밀번호를 채운 뒤 비밀번호를 한 번 출력합니다. 머신에 Node가 없으면 `.env.example` 을 `.env` 로 복사하고 `ADMIN_PASSWORD`(12자 이상), `SESSION_SECRET`, `IMG_PROXY_SIGN_SECRET`, `POSTGRES_PASSWORD`(각각 `openssl rand -hex 32` 로 생성), `LLM_API_KEY` 를 직접 채웁니다.

시작하기 전에 `.env` 의 `SITE_URL` 을 확인합니다. 내 컴퓨터에서 시험할 때는 `http://localhost:3000` 을 그대로 둡니다. 서버에 배포할 때는 독자가 실제로 접속하는 주소로 바꿉니다. 예를 들어 서버 IP로 접속한다면(예시 IP를 자기 것으로 바꿉니다):

```dotenv
SITE_URL=http://192.0.2.10:3000
```

RSS, 공유 링크, 사이트맵, Agent Markdown의 절대 링크는 모두 이 값을 씁니다. 브라우저가 접속한 주소에 따라 저절로 바뀌지 않습니다. 도메인과 HTTPS를 쓸 때는 아래 「도메인과 HTTPS 설정」대로 설정합니다.

설정을 마치면 시작합니다:

```bash
docker compose up -d --build
```

시작한 뒤 `http://서버주소:3000` 을 엽니다. 관리자 화면은 `/admin` 이고, 관리자 비밀번호로 로그인합니다. 처음 시작하면 예시 출처를 불러오고, 1~2분 뒤부터 내용이 나타납니다. 처음 불러온 100여 건의 자료는 처리에 30분쯤 걸립니다(건마다 예비 선별, 점수 매기기, 구조화, 제목·요약 쓰기를 거친 뒤 묶습니다).

`docker compose` 는 컨테이너 다섯 개를 띄웁니다. `db`(PostgreSQL 17), `setup`(시작할 때마다 데이터베이스 마이그레이션과 시드 데이터를 먼저 실행하고 종료), `api`, `worker`(가져오기, 모델 처리, 정기 작업), `web`(웹 페이지)입니다. `web` 은 사이트 주소, API 주소 같은 웹 설정만 받고, API는 HTTP로 읽습니다. 데이터베이스, 모델, 관리자 키, 데이터 볼륨은 백엔드 컨테이너에만 줍니다.

### 중국 본토 서버에서

- 빌드할 때 npm은 중국 내 미러를 씁니다: `docker compose build --build-arg NPM_REGISTRY=https://registry.npmmirror.com`, 그다음 `docker compose up -d`.
- Docker 이미지를 받는 게 느리면 먼저 Docker에 미러 가속을 설정합니다.
- 해외 출처를 가져오지 못하면 `.env` 에 `EGRESS_PROXY_URL` 을 설정합니다. 출처와 이미지를 가져올 때는 이 프록시를 거치고, 모델 API 호출은 거치지 않습니다.
- 웹사이트를 외부에 서비스하려면 먼저 ICP 등록을 마쳐야 합니다. 등록 번호는 `site/site.ts` 의 `icp` 에 적습니다.

### 도메인과 HTTPS 설정

먼저 도메인이 서버를 가리키게 DNS를 설정하고, `.env` 에 다음을 설정합니다:

```bash
SITE_URL=https://example.com
SITE_DOMAIN=example.com
PORT=127.0.0.1:3000        # 3000 포트는 이 머신의 Caddy만 쓰고, 외부에 직접 열지 않습니다
TRUST_PROXY=true           # 방문자 주소는 Caddy가 넘겨 준 요청 헤더에서 읽습니다
```

그다음 HTTPS를 켜서 시작합니다. Caddy가 인증서를 자동으로 발급받고 갱신합니다:

```bash
docker compose --profile https up -d --build
```

이미 Nginx가 있다면 Caddy 대신 사이트를 `http://127.0.0.1:3000` 으로 리버스 프록시하고, `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;` 와 `proxy_set_header X-Forwarded-Proto $scheme;` 를 넣고(관리자 로그인은 이 헤더로 HTTPS 접속인지 판단합니다. 빠지면 로그인 쿠키에 Secure 가 붙지 않습니다), `.env` 에 `TRUST_PROXY=true` 를 설정합니다. `SITE_URL` 은 반드시 독자가 실제로 접속하는 주소로 씁니다. 만들어지는 링크, RSS, 공유 이미지, MCP가 모두 이 값을 씁니다.

MCP는 기본적으로 `SITE_URL` 의 호스트와 `localhost`, `127.0.0.1`, `[::1]` 을 받습니다. 그 밖의 호스트는 `MCP_ALLOWED_HOSTS` 에 쉼표로 구분해 설정합니다. 예: `extra.example:8443,[2001:db8::1]`. 호스트 이름은 대소문자를 가리지 않고, IPv6는 반드시 대괄호로 감쌉니다. 0–65535 범위의 10진수 포트를 붙일 수 있으며, 비교할 때 포트는 무시합니다. 경로, 사용자 정보, 잘못된 포트가 들어간 설정은 적용되지 않습니다. `127.1` 같은 별칭은 명시적으로 넣어야 합니다. 이 설정은 Host 검사에만 영향을 주고, 브라우저 Origin 허용 범위를 넓히지 않습니다.

앞에 Nginx, CDN 같은 캐시가 있다면 앱이 돌려주는 캐시 기한(`Cache-Control`)을 따라야 합니다. 공개 웹 페이지, 내비게이션 데이터, API, RSS, 항목 Markdown, 브리핑 공유 이미지, 사이트맵, 그리고 접속 안내 `/api/v1/agent` 와 `/openapi-v1.json`(5분 기한이 지나면 역시 다시 검증해야 합니다)에는 더 긴 캐시 기한을 따로 붙이지 않습니다. 기한이 지난 뒤 오프라인으로 옛 내용을 돌려주지 않고, 옛 응답을 전달할 때 수명을 새로 세지도 않습니다. 프록시와 CDN이 동적 내용을 겹쳐 캐시하게 두지 않습니다. 프레임워크는 직접 운영하는 사이트의 CDN을 대신 관리하지 않고, 캐시도 대신 비우지 않습니다.

### 업데이트

선택 항목 `PRIVATE_FEED_HOSTS` 가 새로 생겼습니다. 출처의 구독 주소나 목록 주소가 내부망에 직접 띄운 서비스(예: RSSHub)라면 그 호스트 이름을 여기에 적습니다. 사이트 전체의 `ALLOW_PRIVATE_NETWORK_FETCH` 를 켤 필요가 없습니다. 사용법은 [출처](sources.md)를 보세요. 설정하지 않으면 동작은 그대로이고, 데이터베이스 마이그레이션은 필요 없습니다.

주간·월간 브리핑 기간 안에 있어야 할 일간 브리핑이 모두 있는데 원본 본문 항목이 전부 비어 있으면, 그 회차는 자동으로 건너뜁니다. 30분마다 같은 오류가 되풀이되지 않게 하려는 것입니다. 보관함에 빈 주간·월간 브리핑이 새로 생기지 않습니다. 첫 기간은 사이트에서 가장 이른 일간 브리핑부터 검사합니다. 요약할 항목이 없을 때, 일간 브리핑이 빠졌거나, 원래 항목이 나중에 공개할 수 없게 되었거나, 사람이 고치는 중이면 원래 오류를 그대로 남깁니다. 데이터베이스 마이그레이션이나 설정 변경은 필요 없고, 업그레이드 뒤 다음 정기 검사부터 적용됩니다.

본문 네이티브 동영상 수정은 이미 쓸 수 있는 동영상에 재생 컨트롤을 붙이고, 빈 플레이어를 없앱니다. 글에 다시 쓰지 않고 모델도 호출하지 않습니다. 옛 버전이 정리하면서 이미 버린 미디어 주소는 보관본에서 되살릴 수 없습니다. 업그레이드 때 일괄 재추출은 하지 않습니다. 이미 성공한 본문은 추출을 건너뛰고, 내용 해시가 같으면 다시 추출해도 원래 HTML을 유지할 수 있습니다. 앞으로 새 본문은 [출처 안내](sources.md)대로 네이티브 동영상을 남기고, 파일은 계속 브라우저가 원래 사이트에 직접 연결해 받습니다. 서명된 주소는 만료될 수 있습니다.

본문 삽화의 인라인 SVG 그림은 원래 사이트가 써 둔 텍스트 설명을 남기도록 바꿨습니다([출처 안내](sources.md) 참고). 이후에 추출하는 본문에만 적용됩니다. 이미 저장된 본문은 그대로이고, 업그레이드 때 일괄 재추출은 하지 않습니다.

먼저 아래 [백업](#백업) 절에 따라 백업합니다. 빌드가 끝나면 옛 서비스를 멈추고, 마이그레이션과 새 버전 서비스를 실행합니다:

```bash
git pull
docker compose build
docker compose stop api worker web
docker compose run --rm setup && docker compose up -d
```

마이그레이션이 성공한 뒤에 서비스를 시작합니다. 마이그레이션이 실패하면 먼저 오류를 확인하고, 시작을 이어 가지 않습니다. HTTPS 설정을 쓰는 사이트는 `--profile https` 를 계속 붙입니다. 옛 API와 worker는 마이그레이션 전에 멈춰야 합니다. 마이그레이션이 테이블이나 열을 지울 수 있어서, 옛 코드가 돌고 있으면 오류가 납니다. worker를 정상 종료하면 진행 중인 유료 호출이 끝날 때까지 기다립니다(최대 3분 남짓). Docker를 쓰지 않는 배포도 "백업, 빌드, API/worker/web 정지, 마이그레이션(`scripts/migrate.ts`), 시드 데이터(`scripts/seed.ts`), 시작" 순서로 업데이트합니다.

새 마이그레이션이 오래 잠금을 쥔 트랜잭션을 만나면 파일 이름과 대기 시간 초과를 알립니다. 잠금을 쥔 트랜잭션을 먼저 처리한 뒤 setup을 다시 실행합니다. 마이그레이션을 건너뛰거나 마이그레이션 장부를 고치지 않습니다. 동시 인덱스 생성이 중단되면 무효 인덱스가 남을 수 있습니다. 오류에 나온 객체를 확인한 뒤 `DROP INDEX CONCURRENTLY <인덱스이름>` 로 실패한 인덱스를 지우고 다시 실행합니다. 이름은 같지만 정의가 다른 유효한 인덱스는 먼저 차이를 확인해야 합니다. 이런 보호 장치가 위의 Docker 업데이트 순서를 바꾸지는 않습니다. 여러 옛 버전을 건너뛰어 업그레이드하면 과거의 파괴적 마이그레이션이 여전히 실행될 수 있습니다.

아래는 업데이트마다 주의할 점을 최신순으로 적은 것입니다.

일간 브리핑 누락 경보는 베이징 시간 기준 날짜별로 추적하며, 자정을 넘긴다고 저절로 복구되지 않습니다. 해당 일간 브리핑이 있을 때만 복구 알림을 보냅니다. 새 누락 검사는 최근 7개 달력일(오늘 포함)을 보며, 가장 이른 일간 브리핑이나 reports.compose 실행 기록보다 앞서지 않습니다. 이력이 없으면 오늘만 검사합니다. 이미 경보를 보낸 날짜는 이 7일 동안 계속 추적합니다. 수집·모델을 끄거나 worker 시작 유예 기간이 있어도 누락을 복구로 치지 않습니다. 7일이 지나도 일간 브리핑이 없으면 "채우지 못해 알림을 멈춘다"는 알림을 한 번 보내고 더는 알리지 않습니다. 옛 report.daily 상태는 첫 경보 시각을 기준으로 자동 마이그레이션되며, 알림 간격도 유지합니다. 발행 2시간 뒤 경보, 매시간 알림, Feishu 스위치는 그대로입니다. 데이터베이스 마이그레이션은 필요 없습니다. 직접 만든 responder가 옛 `report.daily` 를 정확히 일치시켜 찾는다면 `report.daily:YYYY-MM-DD` 날짜 키를 알아보도록 고쳐야 합니다.

#### 독자 문구의 단어 바꾸기(2026년 10월 9일)

마이그레이션도, 필수 새 환경변수도 없습니다. 분야 패키지에 `industry/wording.ts`(독자 문구에서 쓰지 않을 단어, 템플릿에서는 비어 있음)와 프롬프트 `mend-wording.md` 가 생겼습니다. 병합할 때 이 두 파일이 업데이트와 함께 들어오며, 자기 분야 패키지와 충돌하지 않습니다. 단어 목록이 비어 있으면 검사하지 않고 모델 호출도 늘지 않습니다. 단어를 적으면 그 단어를 쓴 제목, 요약, 추천 이유에 모델 호출이 한 번 더 붙습니다(모델 단계 "단어 바꾸기", 선택 항목 `WORDING_MODEL` 로 모델을 따로 고를 수 있습니다). 설명은 [내 분야로 바꾸기](customize.md)를 보세요.

#### 내비게이션에서 일부 입구 빼기

마이그레이션도, 새 환경변수도 없습니다. `site/site.ts` 에 `NAV.hidden` 이 생겼습니다(지금은 핫이슈 순위 `"/hot"` 와 주제 `"/topics"` 만 지원합니다. [내 분야로 바꾸기](customize.md) 참고). 프레임워크는 `@aihot/site` 에서 이 값을 읽습니다. **`site/site.ts` 를 직접 관리하는 사이트는 병합할 때 템플릿대로 `NAV` 를 추가해야 합니다**. 추가하지 않으면 타입 검사를 통과하지 못합니다. 템플릿에서는 비어 있어 내비게이션은 예전과 같습니다. 입구를 숨겨도 페이지나 공개 API가 꺼지지는 않습니다.

#### 원문 게시물 표시와 엔진 동기화(2026년 10월 6일)

필수 새 환경변수나 데이터베이스 마이그레이션은 없습니다. `site/site.ts` 를 직접 관리하는 사이트는 `REPORTS.quiet` 를 넣어야 하며, 예시 설정을 참고하면 됩니다. 일간 브리핑 시간대 안에 평가를 거친 자료는 있지만 새로운 큰일이 없을 때 평소처럼 발행하고, 이 두 문장을 제목과 도입문으로 씁니다. 도입문의 `{start}`, `{end}` 는 시간대의 시작과 끝입니다. 평가를 거친 자료가 하나도 없으면 여전히 수집이나 판단 실패로 보고, 조용한 하루로 꾸미지 않습니다.

본문이 비어 있고 링크만 있는 X 게시물은 원래의 링크, 이미지, 인용을 그대로 두고, 글쓰기나 번역 모델을 호출하지 않습니다. 출처가 전문 표시를 허용하면 이미지만 있는 게시물도 보여 줄 수 있고, 기존 표시·재배포 허가는 계속 유효합니다. 실제 본문을 얻은 X 장문 글은 평소처럼 처리합니다. 이런 원문 게시물의 공개 페이지에는 옛 번역문도 더는 나오지 않습니다. 이미 잘못된 제목·요약이 만들어진 게시물은 업데이트한 뒤 `packages/backend/src/publication/publish.ts` 의 `publishArticle(id)` 로 공개 내용을 다시 만들 수 있으며, 모델을 다시 호출할 필요는 없습니다.

MCP의 `subscriptions/listen` 은 이제 곧바로 HTTP 404와 JSON-RPC `-32601 Method not found` 를 돌려줍니다. 서비스는 변경을 푸시한 적이 없고, 일반 도구 호출은 그대로 씁니다. 클라이언트는 이 응답을 받으면 상시 구독을 다시 맺으려 하지 말아야 합니다.

데이터베이스가 필요 없는 테스트는 `*.standalone.test.ts` 로 바꿨습니다. `npm test` 는 여전히 백엔드 테스트 전체를 돌리며, 데이터베이스가 필요한 파일에만 복사본을 만듭니다. 이 테스트만 따로 돌리려면 `npm run test:standalone` 을 씁니다.

#### 커뮤니티 수정, 시간 규칙, 읽기 최적화(2026년 10월 4일)

공개 API 버전은 여전히 4.0.0입니다. 필수 새 환경변수는 없고, 선택 항목 `LLM_REASONING_TOKENS` 가 하나 생겼습니다. 아래 `site/models.ts` 항목을 보세요.

**스위치는 `true` 만 인정합니다**: `.env` 의 모든 `*_ENABLED` 스위치(`COLLECT_ENABLED`, `MODEL_CALLS_ENABLED`, `FEISHU_*_ENABLED`, `INDEXNOW_SUBMIT_ENABLED` 등)는 소문자 `true` 로 써야만 켜집니다. 예전에는 `1` 이나 `TRUE` 도 켜짐으로 쳤지만, 이제는 모두 꺼짐으로 봅니다. 업그레이드 전에 `.env` 를 확인해 `true` 로 고칩니다.

**마이그레이션**: 마이그레이션 일곱 개가 새로 생겼습니다. 위 순서대로 setup이 끝나기를 기다리면 됩니다. 모두 데이터를 지우지 않고, 글이나 기존 벡터를 다시 쓰지 않으며, 모델도 호출하지 않습니다. 마이그레이션은 전체 파일 이름으로 장부에 기록하므로, 번호가 같은 다른 파일도 각각 실행됩니다.

- `0055_publication_selected_published_idx.sql`, `0056_analyses_composite_id_idx.sql`, `0056_publications_pool_category_timeline_idx.sql`, `0057_publications_pool_channel_timeline_idx.sql`: 조회 인덱스를 동시 생성하며, 일반 읽기·쓰기를 막지 않습니다.
- `0056_publication_release_selection_stats.sql`, `0057_analyze_publication_release_selection.sql`: 공개 목록용 조회 통계를 만들고 수집합니다.
- `0083_publications_selected_source_idx.sql`: 출처별 엄선 집계용 커버링 인덱스를 동시 생성해, 관리자 화면 통계의 읽기를 줄입니다.

이번에 이 인덱스들과 함께 공개 읽기와 이슈 후보 찾기의 데이터베이스 부담을 줄였습니다. API 내용, 검색 가중치, 이슈 후보 범위는 바뀌지 않습니다.

**이 파일들을 직접 고친 사이트는 병합할 때 새 파일과 대조합니다**:

- `site/site.ts` 에 몇 가지가 생겼습니다:
  - `EDITION_TIMES`, `EDITION_WHEN`: 일간·주간·월간 브리핑의 발행 시각입니다. 원래 코드에 박혀 있었습니다. 일정, 일간 브리핑의 시간 창, 누락 경보, 시간을 언급하는 문구가 모두 이 값을 읽습니다. `public/` 의 파일은 자리표시자 `{{dailyTime}}`, `{{weeklyTime}}`, `{{monthlyTime}}` 을 씁니다.
  - `ITEM_COPY`: 추천 이유를 무엇이라 부를지, 웹 페이지와 공유 이미지에 점수를 보여 줄지 정합니다.
  - `REPORTS.descriptions`, `entry`, `metricUnits`, `shareUnit`: 브리핑 페이지의 설명과 지면의 표현입니다.
  - `ABOUT`, `CARDS` 에서 발행 시각과 추천 이유를 언급하는 문구는 위 항목을 참조하도록 바꿨습니다.
  - `DEPLOYMENT.directImageHosts` 는 `directFetchHosts` 로 이름이 바뀌었고, 수집과 이미지가 이 직접 연결 목록을 함께 씁니다.
  - `SITE.feedbackLead`, `SITE.feedbackEmailHint`: 피드백 페이지 제목 아래 한 줄과 이메일 칸 안내 문구입니다. 원래 코드에 박혀 있었습니다.
  - `SITE.psb`: 선택 항목인 공안 등록 번호입니다. 등록하지 않았거나 해당하지 않으면 `null` 을 적습니다.
  - `ABOUT.lead` 에서 `{sources}` 양옆에 더는 공백을 쓰지 않습니다. 페이지가 자동으로 넣습니다.
- `site/models.ts`: 점수 매기기 호출 인자는 이제 이름 붙은 프리셋의 `scoreCall` 로 설정합니다. `glm-5.3-flash-selection` 을 계속 쓴다면 예시의 온도, 출력 한도, 시간 제한을 맞춥니다. 기존 사용자 모델에 이 항목이 없으면 엔진 기본값을 그대로 씁니다.
- `site/models.ts` 의 `ModelPreset` 과 `site/site.ts` 의 `Founder` 타입은 모두 `@aihot/contracts/site-config` 에서 가져오도록 통일했습니다. 기존 사이트 설정값은 그대로입니다. 이 두 파일을 고쳤다면 타입 import도 맞춰, 엔진에 새로 생긴 선택 필드를 놓치지 않게 합니다.
- 데이터베이스 마이그레이션은 내보내는 중인 `pg_dump` 를 만나면 먼저 기다리며, 최대 대기 시간은 worker 비우기 시간과 같습니다. 시간이 넘으면 이 마이그레이션을 실행하기 전에 종료하니, 내보내기가 끝난 뒤 업데이트 명령을 다시 실행합니다. 다른 잠금은 여전히 바로 오류를 냅니다.
- 마이그레이션은 더는 쓰지 않는 `translation_attempts.request_tag` 열을 지웁니다. 번역 본문, 시도 기록, 유료 영수증은 남습니다. 출처 발행 시각의 원래 정밀도는 따로 저장합니다. 옛 자료에서 정밀도를 알 수 없으면 알 수 없음으로 두고, 0시를 출처가 날짜만 적은 것으로 자동 간주하지 않습니다.
- `site/models.ts`: 추론 모델의 한도는 명시적으로 설정합니다. 기본 모델은 `LLM_REASONING_TOKENS` 를, 이름 붙은 모델은 `reasoningTokens` 를 씁니다. 예전에는 이름이 `-think` 로 끝나는 이름 붙은 모델에만 4000을 더 줬는데, 이 방식은 없앴습니다. 이런 모델을 직접 추가했다면 `reasoningTokens: 4000` 을 넣어야 원래 한도가 유지됩니다. 추론 모델이 한도를 다 쓰면 오류에 `finish_reason=length` 와 고칠 항목이 적힙니다.
- `industry/prompts/story-digest.md`: 이슈 개요의 쓰는 법이 바뀌었습니다. 첫 문장에 핵심 변화와 지금까지의 결론을 밝히고, 필요한 배경을 덧붙이고, 짧은 단락으로 나눕니다. 아래 타임라인을 날짜순으로 되풀이하지 않고, 보도 자체를 평하지 않으며, 분야를 못박아 쓰지도 않습니다. 기존 종합 요약은 일괄로 다시 쓰지 않고, 새 보도가 들어올 때마다 차츰 새 방식으로 바뀝니다. 몇몇 이슈를 바로 다시 쓰고 싶다면 [종합 요약 평가](story-digest-evaluation.md)의 마지막 절을 보세요(`rewriteStoryDigest`, 이슈마다 모델 호출 한 번).
- 직접 관리하는 Compose 파일에서는 `LOCAL_ROUTER_URL` 을 지워도 됩니다. 공유 이미지 예열은 이제 백엔드 렌더러를 바로 재사용하고, 고정된 로컬 포트에 요청하지 않습니다. 이 값을 읽는 코드는 더 없으며, 기본 제공 `docker-compose.yml` 에서도 뺐습니다. 공유 이미지 주소, 형식, 캐시 규칙은 그대로입니다.

**수집과 발행 시각**:

- **첫 가져오기 이후에는 출처의 보관 글을 받지 않습니다**: 예전에는 새 출처를 처음 가져온 뒤, 두 번째 가져오기에서 구독에 남은 옛 항목을 모두 과거 글로 받아 하나씩 유료로 분석했습니다(예시 출처에서 한 번에 천 건이 넘었습니다). 이제 그 뒤 가져오기는 발행 시각이 출처를 처음 가져오기 48시간 전 이내이거나 그 이후인 항목만 받습니다. 날짜가 없는 항목은 그대로 받고, X 계정은 영향이 없습니다. [출처](sources.md#규칙-옛-글이-화면을-덮지-않게)의 "옛 글이 화면을 덮지 않게"를 보세요. 업그레이드 전에 이미 들어온 옛 항목은 원문 시각으로 보관되어 "오늘"과 일간 브리핑에 들어가지 않고, 분석도 이미 끝났으니 따로 처리할 필요가 없습니다.
- **믿을 만한 발행 시각이 없는 새 자료는 일단 공개하지 않습니다**: 공개 목록, 엄선, 브리핑, 핫이슈, 푸시에 먼저 넣지 않고, 원래 출처나 원문 페이지에서 날짜를 읽은 뒤 새 글인지 옛 글인지 판단합니다. 날짜를 모를 때는 글 페이지, 구조화 데이터, Agent Markdown에 "수집 시각"으로 표시하고, RSS에는 `pubDate` 를 쓰지 않습니다. OpenAPI에는 이때 이슈 타임라인과 일간 브리핑 속보의 `publishedAt` 이 수집 시각이라고 적어 둡니다.
- **JSON API의 시간대 없는 시각**(예: `2026-09-30 17:43:58`)은 출처의 `publishedAtUtcOffset` 으로 읽고, 기본값은 `+08:00` 입니다. 예전에는 서버 시간대로 읽었고 Docker 안은 UTC였습니다. 그래서 이런 출처가 이미 있다면 새 항목의 시각이 8시간 앞당겨져 올바른 값이 됩니다.
- **글 페이지 날짜도 같은 출처 시간대를 씁니다**: 상세 페이지 날짜 보충과 본문 추출은 먼저 `detail.publishedAtUtcOffset` 을 쓰고, 없으면 출처의 `publishedAtUtcOffset` 을 이어받으며, 그것도 없으면 `+08:00` 을 씁니다. 이후의 수집과 날짜 보충에만 적용되고, 기존 발행 시각을 일괄로 다시 쓰지 않습니다.
- **상세 보충**: 실패했거나 이번 회차의 횟수 제한을 넘은 날짜, 제목, 요약은 이후 수집에서 채웁니다. 확인된 본문은 그대로 둡니다. 출처 요청은 성공했는데 날짜, 제목, 본문이 빠진 경우에도 채우고, 출처 상태에 기록합니다. Jina 상세 규칙은 실제 응답 형식과 맞아야 합니다. 고정 수집 시작점, Intercom 날짜 장, 동영상 설명 설정은 [출처](sources.md)를 보세요.
- **동영상 재생 페이지는 본문으로 치지 않습니다**: 모든 출처에 적용됩니다. YouTube, Vimeo 재생 페이지는 더는 글 본문으로 가져오지 않고, YouTube 동영상 페이지도 이미지로 보지 않습니다. RSS의 동영상 설명은 요약으로만 쓰고, 구독이 직접 주는 실제 텍스트는 남깁니다. 업그레이드 때 기존 본문을 일괄로 지우거나 다시 분석하지 않습니다. 옛 동영상 기록에 플레이어 내비게이션이 섞였다면 한 건씩 먼저 확인한 뒤, 관리자 화면 "내용 진단"의 상세 페이지에서 요약만 쓰도록 설정해 잘못된 본문 표시를 멈출 수 있습니다.
- **RSS**: 요약이 곧 전문인 것이 확인된 텍스트 구독은 `summaryIsBody` 를 설정할 수 있습니다(Atom의 `summary` 도 해당합니다). 웹 페이지가 없는 팟캐스트 에피소드는 원문 링크를 오디오나 동영상 파일로 바꾸고, 더는 웹 페이지를 가져오지 않습니다.
- **미리보기와 실제 수집이 같은 필터를 씁니다**: 관리자 화면의 "가져오기 미리보기"에도 주소 접두사, 분류, 잡음 단어, 주소 바꿔 쓰기, `publishedAfter` 를 적용합니다. 미리보기에 보이는 항목이 곧 실제 수집이 저장할 항목입니다.
- **수집을 끄면 출처 아이콘도 가져오지 않습니다**: `COLLECT_ENABLED` 가 `true` 가 아니면 매일 04:40 출처 아이콘을 가져오는 작업도 멈추고, 출처 사이트에 더는 접속하지 않습니다.
- **확인된 과거 날짜는 바로잡을 수 있습니다**: 운영 스크립트는 먼저 `admin/content.ts` 의 `previewPublicationDateCorrection` 을 호출하고, 미리보기가 준 버전과 검증값으로 `correctPublicationDate` 를 호출하며, 작업자와 이유를 기록합니다. 옛 날짜와 새 날짜가 모두 7일 창보다 이전인 명확한 정정만 받습니다. 자료 수정 이력, 기사 선정, 묶기는 남기고 모델을 다시 돌리지 않습니다. 자료나 날짜가 바뀌었거나, 이번 정정이 다른 공개 결정을 바꾸게 되면 작업을 거부하고 다시 확인하라고 요구합니다. 일괄 소급 채우기는 없고, 새 공개 API도 없습니다.
- **공개 점수는 사람이 고치거나 취소할 수 있습니다**: 관리자 화면 내용 상세에서 "모델 기준", "점수 취소", "수동 점수"를 지원합니다. 수동 점수는 0–100을 받고, 점수 취소는 공개 값을 `null` 로 만듭니다. 점수 덮어쓰기를 지우면 저장된 모델 점수로 돌아갑니다. 정정할 때는 이유를 적고 버전을 확인해야 합니다. 원래 분석과 감사 기록은 남기고, 웹 페이지, API, RSS, Agent Markdown, MCP를 함께 갱신하며, 모델을 다시 돌리지 않습니다. 기존 글은 업그레이드 때문에 일괄로 점수가 바뀌거나 다시 엄선되지 않습니다.

**공개 출력**:

- **분류 필터는 `PUBLIC_CATEGORIES` 를 따릅니다**: API, RSS, MCP의 `category` 는 공개 API에서 이 분류로 치는 모든 분류를 가져옵니다. 분류를 합치지 않는 사이트(기본값이 이렇습니다)에서는 `tip` 으로 찾아도 더는 의견 글이 딸려 나오지 않습니다. `tip` 분류가 없는 분야도 타입 검사를 통과합니다.
- **지난 브리핑도 다시 검증해야 합니다**: 날짜, 주, 월은 어느 회차인지를 정할 뿐, 내용이 영원히 바뀌지 않는다는 뜻이 아닙니다. 브리핑은 발행 때 쓴 제목과 요약을 유지하고, 출처 이름과 인용 시각은 현재 공개 자료를 따릅니다. 철회된 인용과 그에 기댄 도입글, 표지는 더는 배포하지 않습니다. 브리핑 사본을 보관하는 클라이언트는 `Cache-Control` 이 만료되면 `If-None-Match` 를 붙여 다시 요청합니다.
- **Nginx나 CDN 캐시를 직접 설정한 사이트는 규칙을 확인합니다**: [도메인과 HTTPS 설정](#도메인과-https-설정) 끝부분의 요구대로 점검하고, 업데이트할 때 이 경로들에 이미 있는 프록시·CDN 캐시를 비웁니다. 접속 안내 `/api/v1/agent` 와 `/openapi-v1.json` 도 포함합니다.
- **사이트맵 재생성이 실패해도 옛 파일을 끝없이 쓰지 않습니다**: 프로세스, 디스크 사본, HTTP 응답이 원래의 5분 기한을 함께 씁니다. 기한이 지났는데 다시 만들 수 없으면 `503` 과 `Retry-After` 를 돌려줍니다. MCP는 계속 `no-store` 를 쓰고, API와 Agent 내용은 기한이 지나면 다시 검증합니다.

**도구와 수정**:

- **종합 요약 평가**: `scripts/eval-story-digests.ts` 는 데이터베이스에서 실제 이슈를 내보내, 같은 이슈 묶음에 현재 프롬프트와 후보 프롬프트를 나란히 돌립니다. [종합 요약 평가](story-digest-evaluation.md)를 보세요. 평가 스크립트 세 개는 `scripts/eval-tools.ts` 를 함께 씁니다. `eval-selection.ts` 의 `--n`, `--concurrency`, 모델 이름을 잘못 쓰면 바로 오류를 냅니다.
- **마이그레이션이 읽기·쓰기를 막지 않습니다**: 새 마이그레이션은 파일마다 온라인 실행이 허용된 문장 하나만 담고, 테이블 전체를 소급 채우거나 다시 쓰지 않으며, 인덱스는 `CREATE INDEX CONCURRENTLY IF NOT EXISTS` 로 만듭니다. CI는 `scripts/check-migrations.ts` 로 검사합니다. 통계 관리는 정해진 테이블과 열만 대상으로 합니다. 규칙은 [아키텍처](architecture.md#데이터베이스-마이그레이션)를 보세요.
- MCP 요청에 크기 상한이 생겼고, 오류 로그에서 자격 증명을 뺐습니다.
- 데스크톱 사이드바를 넓히면 얇은 스크롤바가 보입니다.
- 테스트는 각 단계의 실제 프롬프트로 요청을 알아보고, `industry/selection.ts` 에서 문턱을 읽습니다. 분야를 바꿔 프롬프트와 문턱을 고쳐도 더는 잘못 보고하지 않습니다. 아키텍처 테스트도 경로 구분자의 영향을 받지 않습니다.

#### 사이트 파일을 `site/` 로 옮김(2026년 10월 4일)

공개 API는 바뀌지 않았고, 버전은 여전히 4.0.0입니다.

- **사이트 고유 파일을 `industry/` 에서 `site/` 로 옮겼습니다**: `site.ts`, `models.ts`, `brand/`, `pages/`, `public/`, `changelog.json`. `industry/` 에는 분야 지식만 남습니다: `taxonomy.ts`, `topics.json`, `sources.json`, `prompts/`, `selection.ts`. 이 파일들을 고친 적이 있다면 병합할 때 변경 내용을 `site/` 아래 같은 이름의 파일로 옮깁니다.
- **`site.ts` 에 몇 항목이 생겼고**, 모두 비워 둬도 됩니다: `SITE.github`, `SITE.llmsIntro`, `SITE.rootIcons`, `POLICY.terms.license`, `POLICY.terms.headers`, `ABOUT.termsAnchor`(QR 코드 카드에 `alias` 를 쓸 수 있습니다), 그리고 `ACCESS`, `ADMIN`, `DEPLOYMENT`, `FEED_COPY`, `PUBLIC_CATEGORIES`. 설명은 [내 분야로 바꾸기](customize.md)를 보세요. `PUBLIC_CATEGORIES` 는 4.0.0 때의 `publicAs` 를 대신합니다. 원래 분류에 `publicAs: "tip"` 을 썼다면 `PUBLIC_CATEGORIES.merge` 에 씁니다(키는 그 분류의 key, 값은 `"tip"`).
- **`DEPLOYMENT.requiredSecrets`** 는 운영 API가 시작할 때 추가로 확인하는 자격 증명 목록이며, 기본은 비어 있습니다. 기본 세션, 이미지 서명, 관리자 로그인 검사는 그대로 적용됩니다. 배포에서 특정 선택 연동을 반드시 설정해야 할 때만 채웁니다.
- **내 사이트에만 필요한 기능은 모듈로 만들 수 있습니다**: `modules/<이름>/` 에 넣고, `site/modules/` 의 목록에서 켭니다. [아키텍처](architecture.md)의 "모듈"을 보세요. 프레임워크 자체에는 모듈이 없습니다.
- **Agent 접속 페이지는 기본으로 MCP를 엽니다**. 페이지에 MCP, RSS, API 세 가지 접속 방식이 나옵니다. Agent Markdown API는 여전히 `/api/v1/agent` 에 있고, 페이지 아래 "Agent 사용 안내"에서 들어갈 수 있습니다.
- **이미지 프록시에 트래픽 상한을 둘 수 있습니다**: `IMGPROXY_UPSTREAM_MB_PER_MINUTE`, `IMGPROXY_UPSTREAM_GB_PER_DAY`(또는 `site.ts` 의 `DEPLOYMENT.imageUpstreamBudget`). 기본은 설정하지 않습니다.
- **수정**: 같은 데이터는 매번 같은 바이트를 냅니다(정렬에서 동점이 나오면 고유한 순서를 덧붙여, API와 RSS의 ETag가 이유 없이 바뀌지 않습니다). 웹이 api로 넘기는 요청에 홉별 헤더를 더는 붙이지 않아, `Connection: close` 때문에 다음 POST가 실패하지 않습니다. `llms.txt` 의 접속 방식은 실제 개수대로 적고, 더는 네 가지로 쓰지 않습니다.

- **모델 순위, Codex 리셋 모니터링, 주제 페이지의 연표는 더는 프레임워크에 들어 있지 않고**, AIHOT에만 남습니다. 페이지(`/leaderboard`, `/codex-reset`), API(`/api/v1/codex-resets`, `/api/v1/codex-resets/recent`, `/api/v1/agent/codex-resets`), MCP 도구 `<접두사>_get_codex_resets` 를 모두 뺐고, MCP와 `/openapi-v1.json` 의 버전은 4.0.0으로 올랐습니다. 마이그레이션 `0053` 이 이들의 테이블(`lb_*`, `monitor_*`, `fx_rates`)과 설정을 지우고, 정기 작업과 그 실행 대기열은 worker가 시작할 때 자동으로 거둡니다. 관리자 화면 실행 기록은 계속 남습니다. 이 데이터를 남기려면 업그레이드 전에 먼저 백업합니다. 회사 주제 페이지의 로고는 회사 이름 첫 글자로 바뀌었습니다.

#### 공개 API 3.0.0으로 업그레이드(2026년 10월 3일)

- **안전장치는 기본으로 꺼져 있습니다**: `COLLECT_ENABLED`, `MODEL_CALLS_ENABLED` 는 `true` 로 써야만 켜지고, 쓰지 않으면 꺼집니다. `scripts/init-env.ts` 로 만든 `.env` 에는 이 두 줄이 이미 있습니다. 직접 쓴 `.env` 에 없다면 넣어야 합니다. 그러지 않으면 업그레이드 뒤 수집도 모델 호출도 하지 않습니다.
- **주간·월간 브리핑 API의 형태가 바뀌었습니다**: `/api/v1/weeklies`, `/api/v1/monthlies` 의 목록과 각 회차에 `periodStart`, `periodEnd` 가 붙고, 본문은 `sections[]`(칸마다 `label`, `summary`, `items`)로 바뀌었으며, `title`, `themes` 는 더 없습니다. 목록의 `limit` 은 최대 60입니다. 이 두 API를 읽는 프로그램은 함께 고쳐야 합니다. MCP와 `/openapi-v1.json` 의 버전도 이에 따라 3.0.0으로 올랐습니다.
- **엄선의 기계용 출력은 뉴스 하나에 한 건입니다**: API의 `mode=selected`, 동기화 API, 엄선 RSS에서는 같은 뉴스에 대표 보도 하나만 남기고, 다른 보도는 동기화 변경 내역에 `remove` 로 나옵니다(`mode=all` 에는 남아 있습니다). 업그레이드 전에 이미 엄선된 옛 보도는 다시 정리하지 않고, 그 뉴스에 새 보도가 발행될 때 합칩니다.
- **엄선은 중복 확인을 기다립니다**: 점수가 충분한 자료라도, 묶기 단계에서 엄선에 이미 있는 뉴스의 중복이 아니고 새 정보를 담았다고 확인해야 엄선에 들어갑니다. 확인 전에는 "전체 소식"에만 있습니다. 묶기에 쓰는 모델의 답이 형식에 맞지 않으면 거기서 멈추며, 관리자 화면 "실행" 페이지에서 볼 수 있습니다.
- **1차 출처는 등급만 봅니다**: `T1` 이 곧 1차 출처이고, `first_party` 는 더 따로 설정하지 않습니다. 예전에 따로 1차 출처로 표시했던 `T1_5`, `T2` 출처는 더는 1차 출처로 치지 않습니다. 1차로 치려면 `T1` 으로 바꿉니다.
- **분야 패키지에 몇 항목이 생겼습니다**: `taxonomy.ts` 에 `RELEASE`, `PLAIN_TERMS` 가 생겼고, 논평류 분류에는 `commentary: true` 를 표시하며, `ENTITIES` 에 `otherNames` 를 쓸 수 있고, `CATEGORY_BY_ITEM_TYPE` 은 더는 쓰지 않습니다. 이미 다른 분야로 바꾼 사이트는 병합할 때 [내 분야로 바꾸기](customize.md)와 대조해 채웁니다.
- **주제는 `industry/topics.json` 만 읽습니다**: 마이그레이션이 데이터베이스의 `topics` 테이블을 지웁니다. 파일은 그대로 두고 데이터베이스에서만 고친 주제는 업그레이드 전에 파일에 먼저 적습니다. 회사 주제는 `entityId` 만 보고, `related` 는 더는 쓰지 않습니다.
- **일간 브리핑은 더는 모델을 호출하지 않습니다**: 일간 브리핑은 규칙으로 편성하고, 주간·월간 브리핑은 일간 브리핑을 모아 엮습니다. 모델은 총론과 칸별 도입글만 씁니다. 이미 발행한 회차는 다시 쓰지 않습니다.
- **프롬프트가 바뀌었습니다**: `industry/prompts/` 의 `structure.md`, `group-*.md`, `story-digest.md`, `report-period.md` 는 새 방식으로 바뀌었고, `report-daily-lead.md` 는 지웠으며, `report-period-sections.md` 를 새로 넣었습니다. 이 프롬프트를 고친 적이 있다면 대조해서 자기 변경을 옮깁니다.
- **지운 스크립트**: `scripts/delete-sources.ts`, `scripts/regroup-events.ts`, `scripts/enqueue-analysis.ts`. 필요 없는 출처는 관리자 화면에서 일시 정지합니다. 글 한 편의 재평가, 다시 묶기는 관리자 화면 "내용 진단"에서 그 글을 열어 처리합니다.
- **관리자 세션은 로그인 방식에 묶입니다**(마이그레이션 `0041`): 세션 바인딩이 없던 버전에서 업그레이드하면, 묶이지 않은 옛 세션은 다시 로그인해야 합니다. 세션 바인딩 마이그레이션을 이미 시험해 본 데이터베이스는 바로 업그레이드할 수 있습니다. 기존 열과 바인딩은 유지되므로 마이그레이션 기록을 손으로 고칠 필요가 없습니다. 이후의 규칙은 아래 "관리자 세션과 설정 변경"을 보세요.
- **3.x의 `/agent` 는 기본으로 Agent Markdown을 열고**, MCP 접속 안내는 `/agent?tab=mcp` 에 있습니다. 지금의 접속 페이지는 위 "사이트 파일을 `site/` 로 옮김"을 보세요.
- **Feishu 콘텐츠 그룹에는 `T1`, `T1_5` 출처의 엄선만 푸시합니다.**

### 백업

`.env` 에 `DB_BACKUP_STORE_*`(S3 호환 객체 스토리지면 무엇이든)를 설정하면 매일 04:10 그곳에 자동으로 백업합니다. `DB_BACKUP_STORE_SECRET_ID`, `DB_BACKUP_STORE_SECRET_KEY`, `DB_BACKUP_STORE_BUCKET`, `DB_BACKUP_STORE_REGION` 네 항목은 모두 채워야 합니다. `DB_BACKUP_STORE_DOMAIN` 을 채우지 않으면 텐센트 클라우드 COS 방식으로 주소를 만듭니다(`<버킷이름>.cos.<리전>.myqcloud.com`). 다른 S3 호환 스토리지를 쓴다면 그 버킷의 접속 도메인(버킷 이름 포함, 예: AWS S3의 `<버킷이름>.s3.<리전>.amazonaws.com`)을 `DB_BACKUP_STORE_DOMAIN` 에 채웁니다.

완전한 백업 한 번은 같은 타임스탬프의 데이터베이스 `.dump` 와 파일 묶음 `.tar.gz` 로 이루어지며, 파일 이름은 데이터베이스 이름에서 따옵니다. Docker 안의 데이터베이스 이름은 `aihot` 이라서 `aihot-<시각>.dump` 와 `aihot-files-<시각>.tar.gz` 가 됩니다. 파일 묶음에는 `uploads/` 와, 아직 로컬에 저장된 `feedback-screenshots/` 가 들어가며, 이미지 캐시와 로컬 백업 폴더는 들어가지 않습니다. 이미 Feishu로 넘긴 이미지는 데이터베이스의 외부 참조만 남고, 파일 묶음에 Feishu의 이미지를 저장하지 않습니다.

복원할 때는 이 한 쌍의 파일을 함께 가져옵니다. 데이터베이스 버전과 호환되는 `pg_restore` 로 `.dump` 를 빈 데이터베이스에 복원하고, 파일 묶음을 데이터 폴더 최상위(Docker에서는 `/data`, Docker가 아니면 `AIHOT_DATA_DIR`, 기본값 `.data`)에 풉니다. 묶음 안의 하위 폴더 구조를 유지하고, 실행 중인 프로세스가 이 파일을 읽을 수 있게 합니다. 데이터베이스만 복원하면 아직 `local:` 로 참조되는 피드백 스크린숏을 되찾을 수 없습니다. 옛 백업에 들어 있지 않던 파일도 데이터베이스 참조만으로는 복원할 수 없습니다.

아래 수동 내보내기는 데이터베이스만 담고, 위의 첨부 폴더는 담지 않습니다:

```bash
docker compose exec -T db pg_dump -U aihot aihot | gzip > myhot-$(date +%F).sql.gz
```

데이터는 모두 Docker 볼륨 세 개에 있습니다: `db`(데이터베이스), `data`(업로드한 이미지, 이미지 캐시, 로컬 백업), `caddy`(인증서). `docker compose down` 은 이들을 지우지 않지만, `docker compose down -v` 는 지웁니다.

### 관리자 세션과 설정 변경

세션은 로그인 방식, 그리고 로그인 당시의 관리자 자격 증명이나 Feishu 신원에 묶입니다. 관리자 비밀번호, Feishu 관리자 명단, 세션 키를 바꾼 뒤에는 모든 API 프로세스를 다시 시작해 같은 새 설정을 불러오게 해야 합니다. 설정 파일만 고쳤다고 실행 중인 프로세스에 적용된 것은 아닙니다. 옛 코드나 옛 설정을 섞어 쓰는 프로세스로는 권한 회수를 일관되게 할 수 없습니다.

유효 설정이 바뀌면 비밀번호 세션은 옛 비밀번호의 권한을 더는 받지 않고, Feishu 세션은 로그인 때 실제로 받은 union ID나 이메일로 현재 명단을 확인합니다(둘 중 하나라도 여전히 권한이 있으면 됩니다). Feishu 로그인 앱을 끄거나 앱 ID를 바꾸면 Feishu 세션이 무효가 됩니다. 같은 앱의 secret만 교체하면 여전히 권한이 있는 Feishu 세션은 로그아웃되지 않습니다. `SESSION_SECRET` 을 교체하거나 지우면 두 세션 모두 무효가 됩니다.

인증할 때 무효로 확인된 세션은 지워지며, 옛 설정으로 되돌려도 되살아나지 않습니다. 시스템은 전역 자격 증명 변경 이력을 남기지 않습니다. 어떤 설정 변경이 프로세스에 한 번도 적용되지 않았거나, 되돌리기 전에 세션 검사에서 한 번도 관찰되지 않았다면, 그것을 근거로 세션을 소급해 취소할 수 없습니다.

## 비용

- **모델**: 새 자료마다 먼저 예비 선별을 한 번 합니다. 예비 선별을 통과하면 점수를 두 번 매기고, 구조화를 한 번, 제목·요약 쓰기를 한 번 한 뒤 묶습니다(비슷한 보도가 있을 때만 호출합니다). 그 밖에 이슈 종합 요약, 주간·월간 브리핑 총론, 엄선의 전문 번역이 있습니다. 본문이 비어 있고 링크만 있는 X 게시물은 글쓰기나 번역 모델을 호출하지 않습니다. 일간 브리핑은 규칙으로 편성하고 모델을 호출하지 않습니다. 예시 출처로 로컬에서 시험해 보니, 처음 불러온 자료 152건에 모델 호출이 모두 약 930번 들었습니다. 그 뒤 하루에 얼마나 쓰는지는 출처가 하루에 몇 건씩 올라오는지에 달려 있습니다. 관리자 화면 "모델과 평가" 페이지에서 단계마다 호출 횟수와 입출력 token 수를 볼 수 있습니다.
- **유료 가져오기**(X, 위챗 공식계정, Jina): 요청마다 과금되며, 기본으로 꺼져 있고 key를 채워야만 씁니다.
- 모든 유료 서비스에는 분당, 시간당, 하루 호출 상한이 있습니다(관리자 화면 "설정 → 유료 요청 상한"). 넘으면 멈추므로 하룻밤 사이에 청구서가 터지지 않습니다. 0을 적으면 그 서비스를 곧바로 끕니다.

## Docker 없이

Node.js 24.11 이상과 PostgreSQL 16 또는 17이 필요하고, 운영체제는 Linux나 macOS입니다. Windows에서는 WSL2 안에서 돌리거나 위의 Docker 방식을 쓰세요.

```bash
npm ci
node scripts/init-env.ts --llm-key <모델 API 키>
createdb myhot
```

`.env` 에 다음을 추가합니다:

```bash
DATABASE_URL=postgres://<사용자이름>@127.0.0.1:5432/myhot
API_BASE_URL=http://127.0.0.1:3001
```

그다음:

```bash
node --env-file=.env scripts/migrate.ts
node --env-file=.env scripts/seed.ts
npm run build -w @aihot/web

NODE_ENV=production node --env-file=.env apps/api/src/main.ts          # API, 3001 포트
NODE_ENV=production node --env-file=.env apps/worker/src/main.ts       # 백그라운드 작업
cd apps/web && NODE_ENV=production node --env-file=../../.env server.ts   # 웹 페이지, 3000 포트
```

세 프로세스 모두 `NODE_ENV=production` 을 붙여야 합니다. api와 worker는 이것이 없으면 개발 환경으로 돌아갑니다. 시작할 때 운영 키와 관리자 비밀번호를 검사하지 않고, `DEV_AUTH_ROLE` 로그인 생략도 적용됩니다.

세 프로세스는 계속 돌아가야 하므로, 운영 환경에서는 systemd나 pm2로 띄워 둡니다(데몬 설정에도 `NODE_ENV=production` 을 똑같이 설정합니다). worker를 멈출 때는 515초를 줍니다(systemd의 `TimeoutStopSec=515`, pm2의 `kill_timeout: 515000` 과 `treekill: false`). 대기열의 470초 비우기와 데이터베이스 정리를 덮는 시간입니다. systemd는 `KillMode=mixed` 도 설정해, 주 프로세스에만 먼저 작업 받기를 멈추라고 알리고, 백업 중인 `pg_dump`, `tar` 는 저절로 끝나게 합니다. 미리 죽은 호출은 결과를 알 수 없어서, 최소 30분 뒤 자동으로 풀린 다음에야 다시 시도합니다.

개발할 때는 핫 리로드 방식을 씁니다: `npm run dev:api`, `npm run dev:worker`, `npm run dev:web`. 개발 중에 로그인 없이 관리자 화면에 들어가려면 `.env` 에 `DEV_AUTH_ROLE=admin` 을 설정합니다(운영 환경에서는 시작을 거부합니다).
