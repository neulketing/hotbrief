# 내 업계용으로 바꾸기
> 원본 [docs/customize.md](../../../docs/customize.md)(AIHOT, 중국어, 커밋 b868d38)의 한국어 번역입니다. 한국어판에서 바뀌는 부분은 [README.ko.md](../../../README.ko.md)를 보세요.

이 저장소는 기본으로 "AI 업계" 예시 사이트입니다. 예시 출처는 공개된 AI 뉴스 출처 묶음이고, 엄선 기준은 AIHOT 이 AI 분야에서 오래 다듬어 온 그대로입니다. 이것을 "법률 핫이슈", "HR 핫이슈", "금 핫이슈"로 바꾸려면 고칠 것은 거의 다 [`site/`](../../../site/)(이 사이트의 이름, 문구, 브랜드, 페이지)와 [`industry/`](../../../industry/)(업계의 분류, 출처, 프롬프트, 문턱) 두 폴더에 있습니다. 코드는 거의 건드리지 않아도 됩니다.

Claude Code, Codex 같은 에이전트를 쓴다면 아래 글을 그대로 보내고 질문에 답하면 됩니다.

```text
AGENTS.md 와 docs/customize.md 를 읽고 이 사이트를 "OO 업계" 핫이슈 사이트로 바꿔 줘.
내가 신경 쓰는 것: …(지켜볼 출처, 중요한 소식과 아닌 소식, 구체적일수록 좋다)
끝나면 npm run typecheck, npm test, node scripts/smoke.ts 를 돌리고, 아직 내가 정해야 할 것을 알려 줘.
```

아래는 에이전트(또는 직접 하는 사람)가 할 일을 순서대로 적은 것입니다.

## 1. 사이트 이름과 문구: `site/site.ts`

- `name`: 사이트 이름입니다. 내비게이션, 제목, 공유 이미지, RSS, MCP, 관리자 화면이 모두 씁니다. `organization.name` 은 구조화 데이터에 들어가는 사이트 운영자(검색엔진용)이고 기본값도 사이트 이름이라, 사이트 이름을 바꿀 때 함께 바꿉니다. `organization.founder` 는 창업자(선택)이고, 그 안의 `sameAs` 에 공개 개인 페이지 주소를 적을 수 있습니다.
- `subject`: 업계를 가리키는 말입니다. 화면의 "AI 일간 브리핑", "전체 AI 소식"이 "법률 일간 브리핑", "전체 법률 소식"으로 바뀝니다.
- `homeTitle`, `topicsTitle`, `description`, `tagline`, `keywords`: 홈과 주제 목록 페이지의 제목, 한 줄 소개, 공유 이미지 아래 작은 글씨, 검색엔진용 키워드입니다.
- `feedbackExample`: 의견 보내기 입력칸에 보이는 예시입니다.
- `locale`: 화면 언어(웹 페이지 언어 표시, 공유 카드, 구조화 데이터)입니다. `public/` 파일 안의 `{{locale}}` 도 이 값으로 바뀝니다.
- `since`: 사이트가 수집을 시작한 해입니다(구조화 데이터의 기간, 선택).
- `mcpPrefix`: MCP 도구 이름 앞에 붙는 말입니다. 예를 들어 `lawhot` 이면 `lawhot_get_latest` 가 됩니다. 누군가 연결한 뒤에는 바꾸지 않습니다.
- `interfaceVersion`: 공개 API(MCP, OpenAPI, `llms.txt`)의 버전 번호입니다. 올리기만 하고 내리지 않습니다. API 에 이미 있는 필드나 그 뜻을 바꾸면 주 버전을 올립니다.
- `crawlerName`: 출처를 가져올 때 밝히는 이름입니다. 다른 사이트 이름을 쓰지 않습니다.
- `contactEmail`: 외부 연락용 메일 주소(선택)입니다. 넣으면 `llms.txt` 와 에이전트용 안내에 이용 허락 연락처로 적힙니다.
- `footerNote`: 소개 페이지 맨 아래 한 줄입니다. 기본값은 프레임워크 표기 "AIHOT 오픈소스 프레임워크로 구동" 한 줄이고, 남겨도 되고 지워도 됩니다(`null` 로 설정).
- `icp`, `psb`: 중국 본토 사이트의 ICP 등록 번호와 공안 등록 번호입니다. 넣으면 페이지 아래쪽에 보이고 해당 등록 기록으로 연결됩니다.
- `github`: 소스 저장소 주소(선택)입니다. 넣으면 사이드바와 "내 정보" 페이지 맨 아래에 "GitHub 오픈소스"가 나옵니다.
- `llmsIntro`: `llms.txt` 의 한 줄 소개 아래에 붙는 자세한 소개(선택)입니다.
- `rootIcons`: 표준 아이콘 말고도 사이트 루트에 둘 아이콘입니다. `site/brand/` 안의 파일 이름을 적습니다(선택).
- `EDITION_TIMES`: 일간, 주간, 월간 브리핑의 발행 시각(베이징 시간)입니다. 일정, 일간 브리핑의 수집 시간대, 결호 경보, 시간이 들어간 모든 문구가 이 값을 읽습니다. 일정은 30분마다 확인하므로 정각이나 30분으로 씁니다. `EDITION_WHEN` 은 이 값으로 만든 문장용 표현("매일 08:00", "매주 월요일 10:00", "매월 1일 10:30")이고, 보통은 고칠 필요가 없습니다.
- `POLICY`: 이용 규칙과 개인정보 안내 두 페이지의 이름과 소개입니다. `terms.license` 는 어떤 용도에 먼저 허락을 받아야 하는지 밝히는 문장이고, `terms.headers` 는 공개 API 가 이용 규칙을 알리는 응답 헤더입니다(둘 다 선택). `xPostIsFullText` 는 X 게시물 자체의 글을 전문으로 볼지 정합니다(전문으로 보면 출처가 전문을 허락할 때만 보여 줍니다).
- `ABOUT`: 소개 페이지의 큰 제목, 네 단계 설명, 작성자 영역(선택), 저작권 안내, "이용 규칙" 링크의 앵커(`termsAnchor`, 선택)입니다.
- `CARDS`: 각 페이지 공유 이미지에 들어가는 글입니다.
- `NAV`: `hidden` 에는 내비게이션에 넣지 않을 엔진 페이지를 적습니다. 지금은 핫이슈(`"/hot"`)와 주제(`"/topics"`)만 됩니다. 예를 들어 출처가 아직 적어 핫이슈가 자주 비는 사이트는 `"/hot"` 을 적습니다. PC 사이드바, 모바일 하단 바, "내 정보" 페이지 어디에도 넣지 않습니다. 페이지는 그대로 열리고, 그 페이지를 바로 열면 소속 탭은 엄선이 됩니다. 원래 그 페이지로 돌아가던 뒤로 가기 버튼과 링크는 엄선으로 돌아가고, 검색엔진에 주는 페이지 계층(이동 경로)도 그 페이지를 거치지 않습니다. `"/hot"` 을 적으면 홈에도 현재 핫이슈를 넣지 않고, 이슈 페이지에 핫이슈 순위를 적지 않습니다. 기본값은 비어 있고, 내비게이션은 원래와 같습니다.
  다른 페이지는 아직 열어 두지 않았습니다. 그 페이지의 뒤로 가기 버튼과 페이지 안 진입점도 함께 지원해야 하기 때문입니다. 사이드바에서만 숨기고 다른 곳에서는 여전히 독자를 그리로 이끄는 일을 막으려는 것입니다.
- `ITEM_COPY`: 모델이 쓰는 이유 한 문장의 이름(`reasonLabel`, 기본값 "추천 이유")과, 독자가 웹 페이지와 공유 이미지에서 AI 점수를 볼 수 있는지(`showScore`. 보이기만 정하고, 공개 API 와 MCP 에는 그대로 점수가 들어갑니다)입니다.
- `REPORTS.quiet`: 일간 브리핑 시간대에 평가를 거친 자료는 있지만 새 큰 소식이 없을 때의 제목과 도입글입니다. 도입글의 `{start}`, `{end}` 는 시간대의 시작과 끝으로 바뀝니다.
- `REPORTS`: 일간, 주간, 월간 브리핑 지면의 표현입니다. 제호의 발행처 한 줄과 옆의 한 단어, 브리핑 종류별 페이지 설명, 한 호에 실린 한 건을 부르는 말(`entry`, 기본값 "건의 큰 소식"), 제호의 나머지 숫자 뒤에 붙는 단위, 공유 이미지의 건수 표현이 있습니다.
- `ALERTS`, `SOURCE_DEFAULTS`, `COMMUNITY_FEEDS`: 경보에서 배포마다 달라지는 표현, 관리자 화면에서 출처를 새로 만들 때 전문을 보여 줄지의 기본값, 어떤 커뮤니티 사이트 출처를 글쓴 계정별로 열기를 셀지입니다.
- `ACCESS`: 에이전트용 안내와 `llms.txt` 에 들어가는 요청 제한 문구와 권장 User-Agent 입니다. 앞단 리버스 프록시가 실제로 IP 별 요청 제한을 할 때만 `ratePerMinute` 를 적습니다.
- `ADMIN`: 관리자 화면 몇 곳에 보이는 관리자용 안내입니다(선택).
- `AGENT`: 에이전트 연결 페이지 MCP 도구 표의 "검색" 줄 문구입니다. 무엇을 검색할 수 있고 어떻게 물으면 되는지 적습니다.
- `DEPLOYMENT`: 이 배포만의 설정입니다. 자격 증명 파일 위치, 운영 API 가 시작할 때 추가로 확인할 자격 증명(`requiredSecrets`, 기본값 비어 있음), CDN 원본 조회용 도메인, 관리자 로그인 뒤 돌아갈 주소를 담은 요청 헤더, 이미지 프록시의 트래픽 상한, 수집과 이미지를 직접 연결할(외부 프록시를 거치지 않는) 도메인, 엄선 평가에 기본으로 쓸 표본입니다. 모두 비워 둘 수 있습니다.
- `FEED_COPY`, `PUBLIC_CATEGORIES`: "전체 소식" RSS 설명에 덧붙이는, 담지 않는 내용 안내와 공개 API(API, RSS, MCP)에서 웹 페이지와 다르게 쓰는 분류입니다. `merge` 는 한 분류를 다른 분류에 합쳐 내보내고, `feedLabels` 는 분류 RSS 제목에 들어가는 이름을 바꿉니다. 공개한 뒤에는 바꾸지 않습니다.

사이트 주소는 여기에 적지 않습니다. 배포할 때 환경변수 `SITE_URL` 로 정합니다.

## 2. 분류, 태그, 주제: `industry/taxonomy.ts`, `industry/topics.json`

- `CATEGORIES`: 홈과 "전체 소식"의 필터 분류입니다. `key` 는 주소와 API 에 나오므로(`/all?category=`, `/feed/category/<key>.xml`) 공개한 뒤에는 바꾸지 않습니다. `label` 은 화면에 보이는 이름입니다. `section` 은 일간, 주간, 월간 브리핑의 구역입니다(여러 분류가 한 구역을 같이 쓸 수 있습니다). `guide` 에는 이 분류에 무엇을 넣는지, 이웃 분류와의 경계가 어디인지 적습니다. 구조화할 때 모델이 읽습니다(전체 분류 원칙은 `prompts/structure.md` 에 있습니다). `commentary: true` 는 논평류(튜토리얼, 의견)를 표시합니다. 이미 보도한 이슈에 이런 후속 글이 나오면 당사자가 직접 낸 글이라도 일간 브리핑에서는 단신에만 넣습니다(출처 4곳 이상이 보도하면 예외). `feedLabel` 은 분류 RSS 제목에 들어가는 이름입니다(없으면 `label` 을 씁니다). 어떤 분류를 공개 API, RSS, MCP 에서 다른 분류에 합쳐 내보내려면(웹 페이지에서는 그대로 따로 보입니다) `site.ts` 의 `PUBLIC_CATEGORIES` 에 적습니다.
- `RELEASE`: 이 업계에서 가장 주목받는 발표 종류입니다(AI 업계라면 새 모델). 분류와 태그가 모두 맞아야 셉니다. 일간 브리핑 제호의 "새 모델 N개"가 이것으로 셉니다(관리자 화면에서 분류를 고치면 이미 나간 일간 브리핑도 다시 계산합니다). `unit` 은 숫자 뒤에 붙는 말입니다. 이런 종류가 없는 업계는 `null` 로 두면 제호에 이 숫자가 나오지 않습니다.
- `PLAIN_TERMS`: 주간·월간 브리핑의 총평에 바로 써도 되는, 항목에서 출처를 찾지 않아도 되는 업계 일반 용어입니다(소문자). 사이트 이름은 자동으로 포함됩니다. 총평에 항목에 없는 이름이나 숫자가 들어가면 그 총평은 쓰지 않습니다. [엄선과 보정](selection.md)을 보세요.
- `CATEGORY_TAGS`, `TOPIC_TAGS`, `ENTITY_TAGS`: 모델이 태그를 붙일 때 여기서만 고를 수 있습니다. 첫 태그는 반드시 "분류 태그"여야 합니다. `prompts/structure.md` 에도 AI 업계의 태그 규칙(예: 무엇이 "모델 발표"인지)이 적혀 있으니 업계를 바꿀 때 함께 고칩니다.
- `TAG_SYNONYMS`: 모델이 자주 쓰는 비슷한 말을 단어 목록의 표기로 통일합니다(예: "투자 유치"를 "업계 동향"으로). 단어 목록을 바꿨다면 여기도 새 목록의 비슷한 말로 바꿉니다.
- `ENTITIES`: 업계의 주요 회사나 기관입니다. "회사" 주제 페이지에 씁니다. `aliases` 는 구조화하는 모델이 봅니다. `otherNames` 는 그 회사의 다른 이름(공식 계정 이름, 하위 브랜드)입니다. 뉴스의 주체를 회사에 맞추거나, 제목이 이 회사를 이름으로 짚었는지 판단할 때도 이 이름을 인정합니다. `IDENTITY_LEXICON`, `PUBLISHER_DOMAINS`, `IDENTITY_CONTEXT_ALIASES` 는 모델이 원문에 없는 회사를 제목과 요약에 써 넣지 못하게 막습니다. 제목과 요약에 나온 회사는 원문에도 나와야 합니다. `IDENTITY_CONTEXT_ALIASES` 에는 원문에 나오면 이 회사를 언급한 것으로 보는 표기(예: 공식 계정 이름)를 적습니다. 이런 필요가 없는 업계라면 비워도 됩니다.
- `ITEM_TYPES`: 콘텐츠 유형입니다. 점수 매기기 프롬프트의 가중치 표와 짝이 맞으니, 고치면 프롬프트도 함께 고칩니다.
- `topics.json`: 주제 목록(`/topics`)입니다. 사이트가 시작할 때 읽으므로 고친 뒤 다시 빌드해야(`docker compose up -d --build`) 반영됩니다. 세 묶음으로 나뉩니다. `company`(회사와 기관), `field`(분야), `genre`(콘텐츠 형태)입니다. `slug` 는 공개한 뒤에는 바꾸지 않습니다.
  - `company` 주제는 `entityId`(`ENTITIES` 의 id)로 이 회사가 주체인 보도를 모읍니다. 한 보도의 주체가 여러 회사이면 제목에 그 회사 이름이 나와야 셉니다. 선택 항목으로 `aliases`(검색창에서 이 말만 검색해도 이 회사의 보도가 나옵니다)가 있습니다.
  - `field` 와 `genre` 주제는 `tags` 로 이 태그가 붙은 보도를 모읍니다.

## 3. 출처: `industry/sources.json`

처음 시작할 때 가져오는 예시 출처입니다. 이미 있는 출처는 덮어쓰지 않습니다. 그 뒤로는 시작할 때마다 파일에는 있고 데이터베이스에는 없는 것만 더합니다. 파일에서 지운 출처는 데이터베이스에서 지워지지 않습니다(쓰지 않을 출처는 관리자 화면에서 멈춥니다). 공개한 뒤에는 관리자 화면 "출처" 페이지를 더 자주 씁니다. 새로 만들기, 시험 가져오기, 주기 조정, 멈추기, 실패 이유 보기가 됩니다.

출처마다 중요한 필드는 다음과 같습니다.

| 필드 | 뜻 |
|---|---|
| `kind` | `rss`, `web_list`(웹 목록, 선택자 설정), `json_list`(JSON API), `x_search`(X 계정, SocialData 필요), `mp_account`(위챗 공식계정, Dajiala 필요), `external`(외부 푸시) |
| `config` | 출처 종류별 설정입니다. [출처](sources.md)를 보세요 |
| `tier` | 출처 등급입니다. `T1` 공식 1차 출처, `T1_5` 공식 계정과 준공식, `T2` 언론과 개인, `EXCLUDE_MP` 엄선에 참여하지 않음. 등급마다 엄선 문턱이 다릅니다. `T1` 이 곧 "1차 출처"이므로 따로 표시하지 않습니다 |
| `owner_entity_id` | 선택 항목입니다. 이 출처가 어느 회사 것인지(`ENTITIES` 의 id) 적습니다. 같은 회사의 여러 출처는 열기에서 참여자 하나로 칩니다. `T1_5` 공식 계정을 대표 보도로 쓰려면 이것도 적어야 합니다([출처](sources.md) 참고) |
| `participation_mode` | `editorial` 은 엄선과 전체 소식에 들어갑니다. `hot_signal` 은 열기의 근거로만 씁니다. `isolated` 는 어떤 공개 페이지에도 들어가지 않습니다 |
| `site_fulltext` | 사이트 안에서 전문을 보여 줄 수 있는지입니다. **기본값은 꺼짐**이고, 요약과 원문 링크만 보여 줍니다. 출처가 분명히 허락할 때만 켭니다 |
| `syndicate_fulltext` | 전문 RSS 에 본문을 넣을 수 있는지입니다. **기본값은 꺼짐**입니다. 사이트 안에서도 전문을 보여 줄 때만 효과가 있고, 출처가 전재를 분명히 허락할 때만 켭니다 |

중국 본토의 많은 업계는 1차 정보가 위챗 공식계정에 있습니다. 위챗 공식계정 출처에는 极致了(Dajiala) 키가 필요합니다. 요청마다 요금이 나오고, 예산 차단 장치가 있습니다.

가장 시간을 들일 만한 단계입니다. 이 업계를 보는 내 판단 경험을 여기에 적습니다.

| `selection-score.md` | **점수 기준**: 0–100점을 줍니다. 콘텐츠 유형, 다섯 가지 차원, 유형별 가중치, 반드시 제대로 평가해야 할 가치, 반드시 눌러야 할 잡음이 들어 있습니다 |
| `content-understanding.md` | 엄선된 콘텐츠와 엄선에 가까운 콘텐츠를 쓰는 법: 중국어 제목, 답부터 말하는 요약, 추천 이유(태그도 붙이지만, 화면의 분류와 태그는 `structure.md` 에서 옵니다) |

| `translate-*.md` | 전문 번역 |

내 사이트의 독자용 글에 쓰지 않을 말(과장된 표현, 사투리, 독자가 모르는 업계 은어)이 있다면 `industry/wording.ts` 에 적습니다. 항목마다 정규식 하나와 고치는 법입니다. 제목, 요약, 추천 이유를 다 쓴 뒤 하나씩 확인하고, 쓰였으면 모델이 그 말만 한 번 고치게 합니다(모델 단계 "표현 고치기", 환경변수 `WORDING_MODEL` 로 모델을 따로 고를 수 있습니다). 고친 뒤 숫자가 바뀌었거나, 제목이나 요약이 비었거나, 모델 서비스가 고쳐 쓰기를 거부하면 원래 글을 그대로 둡니다. 단어 목록이 비어 있으면 확인하지 않고 호출도 늘지 않으며, 모델 서비스가 서비스를 거부할 때의 경보에도 이 단계를 적지 않습니다.

프롬프트 안에서 `{{siteName}}` 은 사이트 이름을 가리키고, `{{> 파일이름}}` 은 다른 프롬프트를 불러옵니다. 프롬프트를 고칠 때 코드는 고치지 않아도 됩니다.

**권장하는 방법**: 먼저 구조(다섯 차원 가중치, 잡음 누르기 규칙, 안전 경계)는 그대로 두고, "무엇이 중요한가", "무엇이 잡음인가"의 예시만 내 업계 것으로 바꿉니다. 예를 들어 법률 업계라면 "새 법규 공식 공포, 중요 판결, 규제 처분"은 제대로 평가해야 하고, "로펌 홍보성 기사, 강좌 광고"는 눌러야 합니다.

## 5. 문턱과 보정: `industry/selection.ts`

두 번 매긴 점수의 합이 2 × 문턱 이상이어야 점수가 충분합니다(점수가 충분한 것도 묶을 때 중복 제거를 통과해야 합니다. [엄선과 보정](selection.md)을 보세요). 기본 문턱(T1 60, T1_5 65, T2 76)은 AIHOT 이 AI 분야에서 보정한 값입니다. 업계와 프롬프트를 바꿨다면 다시 보정해야 합니다.

1. 내 출처에서 자료 100–200건을 골라 직접 "뽑아야 함 / 뽑지 말아야 함"을 라벨링하고 `.data/gold.jsonl` 로 저장합니다(형식은 [엄선과 보정](selection.md), 예시 두 건은 `industry/gold.example.jsonl`).
2. `node --env-file=.env scripts/eval-selection.ts --gold .data/gold.jsonl` 을 실행해 정확도, 정밀도, 재현율과 문턱별 결과를 봅니다.
3. 관리자 화면 SelectBench 에서 잘못 판단한 자료를 하나씩 보고, 점수 프롬프트나 문턱을 고친 뒤 다시 돌립니다.

이 단계가 내 사이트가 "제대로 고르는지"를 정합니다.

- `nameplates/`: 일간, 주간, 월간 브리핑 페이지 맨 위의 제호 글자(예: "AI일간")입니다. 업계를 가리키는 말을 바꿨다면 다시 만듭니다.

AIHOT 의 이름과 로고는 쓰지 마세요.

독자는 "내 정보" 페이지에서 글꼴을 "기본 글꼴"에서 "브라우저 기본 글꼴"로 바꿀 수 있습니다. 뒤의 것은 독자가 브라우저에서 정한 표준 글꼴을 쓰고, 일반 본문, 입력 양식, 움직이는 차트 글자에 적용됩니다. 코드는 그대로 고정폭 글꼴이고, 로고, 제호 글자, 공유 이미지는 사이트 브랜드대로 보입니다. 글꼴 선택은 지금 브라우저에만 저장되고, 간체·번체는 바꾸지 않습니다. 즐겨찾기 페이지의 버전 1 백업에 선택 필드 `font` 가 생겼고, 예전 백업도 그대로 가져올 수 있습니다. 가져오기는 독자가 이미 고른 브라우저 글꼴을 덮어쓰지 않습니다.

## 7. 페이지 문구: `site/pages/`, `site/public/`, `site/changelog.json`

- `pages/terms.md`, `pages/privacy.md`: 이용 규칙과 개인정보 안내입니다. **지금은 템플릿**이니 공개 전에 실제 상황에 맞게 고쳐 쓰고, 필요하면 전문가에게 보여 주세요.
- `public/`: 사이트 루트에 두는 고정 파일 네 개입니다. 자리표시자를 바꾼 뒤 공개합니다. `robots.txt`, `manifest.webmanifest`(휴대폰 홈 화면에 설치할 때의 이름과 아이콘), `openapi-v1.json`(공개 API 설명), 그리고 선택 파일 `.well-known/security.txt`(보안 문제 연락처)입니다. 이 네 파일만 공개하고, 다른 파일을 넣어도 사이트에 나오지 않습니다. 없는 파일은 열면 404 입니다. 파일 안에 쓸 수 있는 자리표시자는 `{{siteName}}`, `{{siteUrl}}`, `{{description}}`, `{{tagline}}`, `{{locale}}`, 발행 시각 `{{dailyTime}}`, `{{weeklyTime}}`, `{{monthlyTime}}`, 공개 API 버전 `{{version}}`, 쉼표로 구분한 공개 분류 `{{categoryList}}` 입니다. JSON 파일의 `enum` 이나 `examples` 목록 안에 있는 `"{{categories}}"` 는 공개 분류 key 목록으로 바뀝니다.
- `changelog.json`: 업데이트 기록입니다. "사이트 공개" 예시가 하나 들어 있으니, 공개 전에 그 `date`, `time`, `latestVersion` 을 내 공개 시각으로 바꿉니다. 예시 본문의 프레임워크 표기("AIHOT 오픈소스 프레임워크로 이 사이트를 만들었습니다")도 남겨도 되고 지워도 됩니다. 새 항목은 맨 앞에 쓰고 `latestVersion` 을 그 날짜와 시각으로 바꿉니다. `kind` 는 "업데이트", "개선", "공지", "종료" 중 하나입니다. 독자가 꼭 봐야 하는 항목에는 `"urgent": true` 를 붙입니다(빨간색, "중요" 표시).

## 8. 모델과 배포

- 모델: `.env` 의 `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL` 입니다. OpenAI 호환 API 라면 무엇이든 되고, 모든 단계가 기본으로 이것을 씁니다. `site/models.ts` 에는 이름 붙은 모델(각자 자기 주소와 키 환경변수를 씀)과 단계별 기본 모델이 적혀 있습니다. 배포할 때 환경변수(`.env.example` 참고)나 관리자 화면 "모델과 평가" 페이지에서 단계마다 바꿔 고를 수도 있습니다. 추론 모델(먼저 생각하고 답하는 모델)을 쓰면 추론할 몫을 남겨 둡니다. 기본 모델은 `LLM_REASONING_TOKENS` 를, 이름 붙은 모델은 `site/models.ts` 에 `reasoningTokens` 를 적습니다. 남겨 두지 않으면 추론이 단계마다 출력 한도를 다 써서 답이 비고, 호출이 매번 실패합니다. 점수 매기기 프리셋에는 `scoreCall: { temperature, maxTokens, timeoutMs }` 도 적을 수 있고, 각각 온도, 출력 한도, 제한 시간(밀리초)을 정합니다. 예시 점수 매기기 프리셋에는 이 값들이 명시돼 있습니다. 예비 모델의 `fallbackFor` 는 능력 이름으로 넘겨받을 주 모델을 지정합니다. 이 조합은 먼저 내 자료로 평가해야 합니다. 예시 사이트에는 기본으로 예비 조합이 없습니다.
- 배포: [배포](deploy.md)를 보세요.

## 고친 뒤 확인

```bash
npm run typecheck
DATABASE_URL=postgres://…/myhot_test npm test     # 데이터베이스 이름은 _test 또는 _ci 로 끝나야 하고, 데이터베이스 계정은 데이터베이스를 만들 수 있어야 한다
node scripts/smoke.ts --base http://localhost:3000   # 사이트가 돌아가기 시작한 뒤
```

프롬프트를 고쳐 쓰거나 문턱을 다시 보정해도 테스트는 실패하지 않습니다. 테스트는 단계마다 실제로 렌더링된 프롬프트로 요청을 알아보고, 문턱은 `industry/selection.ts` 에서 읽기 때문입니다. `tests/` 의 일부 테스트는 예시 업계의 분류, 태그, 회사(예: `ai-models`, "모델 발표", Anthropic)를 씁니다. `industry/taxonomy.ts` 를 고치면 이 테스트들이 실패하니, 예시를 내 업계의 해당 항목으로 바꾸면 됩니다. 테스트하는 규칙 자체는 고치지 않아도 됩니다.

그다음 사이트를 열어 홈, 전체 소식, 일간 브리핑, 주제 페이지, 소개 페이지를 한번 보고, 관리자 화면 "출처" 페이지에서 출처를 모두 잘 가져왔는지 확인합니다.
