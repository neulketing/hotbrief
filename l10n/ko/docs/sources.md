# 출처

> 원본 [docs/sources.md](../../../docs/sources.md)(AIHOT, 중국어, 커밋 b868d38)의 한국어 번역입니다. 한국어판에서 바뀌는 부분은 [README.ko.md](../../../README.ko.md)를 보세요.

출처는 관리자 화면의 "출처" 페이지에서 관리합니다. 새로 만들고, 한 번 시험 삼아 가져와서 무엇이 들어오는지 보고, 빈도를 바꾸고, 켜고 끄고, 실패 원인과 최근 항목을 봅니다. 처음 시작할 때 `industry/sources.json` 에 있는 예시 출처를 불러옵니다.

## 여섯 가지 출처

| 종류 | 맞는 곳 | 필요한 것 |
|---|---|---|
| `rss` | RSS / Atom 이 있는 블로그, 매체, Substack, 위챗 공식계정을 RSS 로 바꿔 주는 서비스 | 없음 |
| `web_list` | RSS 가 없는 웹 목록(뉴스 페이지, 블로그 목록, 업데이트 기록) | 선택자를 씁니다. 필요하면 Jina Reader 렌더링을 설정합니다(건당 과금) |
| `json_list` | JSON 을 돌려주는 API(GitHub Releases 등) | 필드 경로를 씁니다 |
| `x_search` | X(트위터) 계정 | SocialData 키, 요청당 과금 |
| `mp_account` | 위챗 공식계정 | 极致了(Dajiala) 키, 요청당 과금 |
| `external` | 직접 만든 스크립트가 푸시해 넣는 내용 | `INGEST_TOKEN`, 아래 참고 |

`json_list` 의 주소나 설정에는 자격 증명이 들어 있을 수 있어서, 같은 출처로 가는 리디렉션(프로토콜, 호스트, 포트가 모두 같은 것)만 따라갑니다. API 가 다른 출처로 옮겨 갔다면 출처 주소를 직접 고칩니다. 다른 출처로 넘어가는 리디렉션에 인증 정보를 실어 보내는 방식에 기대지 않습니다.

가져오기는 기본적으로 내부망 주소에 접속하지 않습니다. 구독 주소나 목록 주소가 내부망에 직접 띄운 서비스를 가리키면(예: 같은 Docker 네트워크의 RSSHub, 주소는 `http://rsshub:1200/...`) `.env` 에 `PRIVATE_FEED_HOSTS=rsshub`(쉼표로 구분한 전체 호스트 이름, 대소문자 구분 없음)를 설정하고 API 와 worker 를 다시 시작합니다. 이 허용은 `rss` 의 `feedUrl`, `web_list` 와 `json_list` 의 `url` 자체에만 적용됩니다. 이 호스트들은 직접 접속하고 `EGRESS_PROXY_URL` 을 거치지 않습니다. 다른 호스트로 넘어가는 리디렉션, 기사 본문, 상세 페이지, 이미지와 아이콘은 여전히 원래 규칙대로 내부망 주소를 거부합니다. 링크 로컬 주소와 클라우드 메타데이터 주소(`169.254.0.0/16`, `100.100.100.200` 등)는 언제나 거부합니다.

출처 종류마다 어떤 설정 항목을 받는지는 [`config-keys.ts`](../../../packages/backend/src/sources/config-keys.ts)에 적혀 있습니다. 모르는 설정 항목을 넣으면 저장이 거부되고, 가져오기는 바로 실패하며 관리자 화면에 원인이 나옵니다. 몰래 일반 파싱으로 물러나지 않습니다.

## 먼저 미리 보고, 그다음 만들기

`/admin/sources/new` 에 들어가 ID 와 이름을 채우고 종류를 고른 뒤, [다음 절](#출처-종류별-설정)에서 해당하는 JSON 을 "수집 설정(JSON)"에 넣습니다. 여기에 넣는 것은 설정 객체입니다. `kind` 나 `config` 로 감싸지 않습니다. 종류를 바꾸면 설정이 초기화되니 종류를 먼저 고르고 붙여 넣습니다.

이름 안의 전각 괄호 속 메모(예: "어느 매체（핫이슈 RSS）")는 관리자 화면에서만 보입니다. 독자는 웹페이지, RSS, Agent Markdown, MCP, 검색에서 메모를 뺀 이름을 봅니다. X 계정을 `X：표시이름 (@handle)` 형식으로 쓰면 독자는 표시 이름만 봅니다. 공개 API 의 JSON 에는 여전히 전체 이름이 들어 있습니다.

`rss`, `web_list`, `json_list`, `x_search` 는 "미리 수집"을 누를 수 있습니다. 항목 총수와 앞 20개의 제목, 원문 링크, 발행 시각, 요약을 보여 주고, 항목을 기사 저장소에 넣지는 않습니다. 들어온 것이 내비게이션이 아니라 기사인지, 날짜가 원문과 같은지 확인한 뒤 "만들기"를 누릅니다. 미리 보기와 정식 수집은 같은 필터(주소 접두어, 분류, 잡음 단어, 주소 고쳐 쓰기, `publishedAfter`)를 씁니다. 보이는 것이 곧 정식 수집이 받을 항목입니다. 다만 미리 보기를 했다고 실제 수집을 마친 것은 아니고, 이후의 상세 보충, 엄선, 공개 발행 과정도 거치지 않습니다.

미리 보기도 가져오기 요청을 보냅니다. X 와 Jina 미리 보기는 비용이 들 수 있고, 유료 영수증과 예산을 거칩니다. `COLLECT_ENABLED=false` 는 관리자 화면의 자동 수집만 끕니다. 이것으로 수동 미리 보기가 외부 서비스에 접속하지 않는다고 보장할 수는 없습니다. 아래의 로컬 HTML/JSON 예시는 API 키가 필요 없습니다.

## 출처 종류별 설정

### rss

```json
{ "feedUrl": "https://example.com/feed.xml" }
```

선택 항목: `summaryIsBody`(텍스트 구독의 요약이 곧 전문이라고 확인했을 때, RSS 의 `description`, Atom 의 `summary` 를 본문으로 쓰고 원문 페이지를 다시 가져오지 않습니다), `allowCategories` / `denyCategories`(구독에 적힌 분류로 거릅니다).

어느 출처든 YouTube, Vimeo 영상 재생 페이지는 기사 본문으로 추출하지 않습니다. Media RSS 의 영상 설명은 요약으로 남깁니다. `summaryIsBody` 를 설정해도 설명을 영상 자막으로 여기지 않습니다. 구독이 `content` / `content:encoded` 로 주는 실제 텍스트는 그대로 쓸 수 있습니다. 다른 기사 안에 영상이 박혀 있어도 그 기사의 본문 읽기에는 영향이 없습니다.

기사 본문 안의 네이티브 영상은 안전한 미디어 주소와 후보 형식을 남기고, 브라우저 컨트롤로 직접 재생합니다. 영상 파일은 브라우저가 원래 사이트에서 바로 받고, 표지는 이미지 프록시를 그대로 씁니다. 자동 재생과 반복 재생은 하지 않고 미리 불러오기 힌트는 `none` 으로 둡니다. 다만 브라우저가 상호작용 전에 요청을 전혀 보내지 않는다고 보장하지는 않습니다. 미디어 주소도, 쓸 수 있는 표지도 없는 플레이어는 대체 텍스트만 남깁니다. Markdown 과 재배포가 허용된 전문 RSS 는 영상 구조를 남기고, 재생이 되는지는 리더에 달려 있습니다. 동적 플랫폼 플레이어와 iframe 은 여기에 들어가지 않습니다.

기사 삽화 안에 들어 있는 SVG 그림은 그림 자체를 남기지 않습니다(색과 글꼴이 원래 사이트의 스타일시트에 달려 있습니다). 대신 원래 사이트가 이 그림에 붙인 접근성 설명(`aria-label`, `aria-labelledby` 가 가리키는 텍스트, 또는 그림 안의 `<title>`, `<desc>`)을 일반 텍스트로 그림이 있던 자리에 둡니다. 같은 그림의 넓은 판과 좁은 판은 하나만 남기고, 삽화에 이미 보이는 텍스트(그림 설명, 소제목)는 되풀이하지 않습니다. 텍스트 설명이 없는 그림과 삽화 밖의 SVG 아이콘은 전처럼 지웁니다.

웹페이지가 없는 팟캐스트 에피소드(`<link>` 가 없고 `guid` 도 웹 주소가 아닌 것)는 오디오나 영상 파일을 원문 링크로 써서 브라우저에서 바로 재생할 수 있게 합니다. 이런 에피소드는 웹페이지를 가져오지 않고 구독에 있는 텍스트로 처리합니다.

### web_list

일반 CSS 선택자를 지원하고, `div` 목록도 수집할 수 있습니다. 핵심은 `itemSelector` 가 모든 뉴스를 감싼 컨테이너가 아니라 **뉴스 하나하나**를 골라야 한다는 점입니다. 예:

```html
<div class="news-list">
  <div class="news-item">
    <h2><a href="/posts/first">第一条示例新闻</a></h2>
    <time datetime="2026-10-01T09:00:00+08:00">10 月 1 日</time>
  </div>
  <div class="news-item">
    <h2><a href="/posts/second">第二条示例新闻</a></h2>
    <time datetime="2026-10-01T10:00:00+08:00">10 月 1 日</time>
  </div>
</div>
```

이에 맞는 설정(`example.com` 은 자리 표시용 주소이니 대상 웹페이지로 바꿉니다. 실제로 돌아가는 판은 [로컬 예시](#htmljson-예시를-로컬에서-돌려-보기)에 있습니다):

```json
{
  "url": "https://example.com/news",
  "parseMode": "html",
  "itemSelector": ".news-list > .news-item",
  "linkSelector": "h2 a",
  "titleSelector": "h2 a",
  "publishedAtSelector": "time",
  "allowUrlPrefixes": ["https://example.com/posts/"]
}
```

- `itemSelector` 는 페이지 전체에서 항목을 찾습니다. `linkSelector`, `titleSelector` 는 각 항목 안에서 처음 맞는 노드를 고르고, 항목 자신과 맞아도 됩니다. `.news-list` 를 고르면 컨테이너 하나만 잡혀서 보통 첫 뉴스만 나옵니다. `div` 만 쓰면 중첩된 컨테이너가 섞입니다. 되풀이해 나오는 뉴스 노드를 골라야 합니다.
- 링크는 `href` 에서 가져옵니다. `/posts/first` 같은 상대 링크는 목록이 리디렉션된 뒤의 최종 주소를 기준으로 풀고, `baseUrl` 로 기준 주소를 정할 수도 있습니다. 제목은 노드의 텍스트를 씁니다. 같은 링크는 하나로 합칩니다. Markdown 목록에서 "Read more" 같은 버튼이 먼저 나오고 진짜 제목이 뒤에 나오면 진짜 제목을 씁니다. 목록 자신을 가리키는 링크는 보통 건너뜁니다.
- 날짜는 항목 안에서 `publishedAtSelector` 를 찾아 `datetime`, `content`, `title` 속성과 텍스트를 차례로 시도합니다. 파싱할 수 없는 안내 문구가 같은 노드의 유효한 날짜를 가리지 않습니다. 시간대가 없는 날짜·시각에는 `publishedAtUtcOffset`(기본 `+08:00`)을 쓸 수 있습니다. 시간대가 붙은 시각은 원래 시간대의 뜻을 그대로 지키고, 순수한 `YYYY-MM-DD` 는 UTC 0시로 읽습니다. 불완전한 월, 제품 버전 번호, 달력에 없는 날짜는 발행일로 쓰지 않습니다.
- `parseMode`: 일반 웹페이지는 기본이 `html` 입니다. `markdown` 은 Markdown 링크로 읽습니다. `docusaurus_changelog` 는 업데이트 기록의 제목을 읽습니다. `intercom_changelog` 는 Intercom 도움말 센터의 날짜 절을 따라 제목과 본문을 읽고, 절마다 자기 웹 주소 앵커를 지킵니다. 기본으로 UTC 달력 날짜로 읽고, `publishedAtUtcOffset` 을 정할 수도 있습니다. Jina 가 필요하면 `url` 을 `https://r.jina.ai/https://대상사이트/경로` 처럼 명시적으로 쓰고 `JINA_API_KEY` 를 설정합니다. 가져오지 못했다고 자동으로 바뀌지 않습니다. Jina 는 기본으로 Markdown 을 돌려줍니다. CSS 선택자를 계속 쓰려면 `parseMode: "html"` 을 명시적으로 설정합니다.
- `detail`: 목록에 날짜, 제목, 요약이 없을 때 상세 페이지를 가져와 채웁니다(`publishedAtSelector`, `titleSelector`, `summarySelector` 등). `maxFetches` 는 한 번 돌 때 상세 페이지를 최대 몇 편 읽을지입니다. 설정하지 않으면 0, 즉 한 편도 읽지 않습니다. 한 편 읽을 때마다 요청이 하나 늘어나므로 출처가 직접 밝혀야 합니다. 읽기에 실패했거나 이번 회차 `maxFetches` 를 다 쓴 항목은 다음 가져오기에서 계속 채웁니다. 메타데이터를 채울 때 이미 확인한 본문은 남깁니다. 이미 진짜 제목이 있으면 목록에 여전히 "Read the Blog" 라고 적혀 있어도 버튼 문구로 되돌리지 않고, 제목이 길다는 이유만으로 상세 페이지를 다시 읽지도 않습니다. 상세 페이지 제목을 꼭 쓰게 하려면 `titleAuthoritative: true` 를 설정합니다. 상세 페이지와 본문 추출에서 시간대 없는 시각을 읽으면 먼저 `detail.publishedAtUtcOffset` 을 쓰고, 없으면 출처의 `publishedAtUtcOffset` 을 이어받으며, 둘 다 없으면 기본 `+08:00` 입니다. RSS, JSON 목록에도 `detail` 을 쓸 수 있습니다.
- Jina 목록의 `detail.titleRegex`, `publishedAtRegex` 는 Jina 텍스트와 맞춰 보고, 같은 상세 응답 한 번을 함께 쓸 수 있습니다. CSS 선택자는 원래 사이트의 HTML 을 읽습니다. 실제로 읽을 수 있는 페이지에 맞춰 규칙을 고릅니다.
- `allowUrlPrefixes` / `denyUrlPrefixes`: 특정 경로 아래의 기사만 받습니다.

### json_list

API 가 아래 구조를 돌려준다고 합시다. `itemsPath` 는 배열을 가리키고, 다른 필드 경로는 **배열 원소 하나하나**를 기준으로 씁니다. 경로는 점으로 구분하며 JSONPath 가 아닙니다. `$` 나 `[*]` 는 쓰지 않습니다.

```json
{
  "data": {
    "items": [
      {
        "id": "first",
        "title": "第一条示例新闻",
        "url": "https://example.com/posts/first",
        "summary": "第一条新闻的摘要。",
        "published_at": "2026-10-01T09:00:00+08:00"
      }
    ]
  }
}
```

이에 맞는 설정:

```json
{
  "url": "https://example.com/api/news",
  "mode": "json_api",
  "itemsPath": "data.items",
  "titlePaths": ["title"],
  "urlTemplate": "{raw:url}",
  "summaryPaths": ["summary"],
  "publishedAtPath": "published_at",
  "externalIdPath": "id"
}
```

- API 가 배열을 바로 돌려주면 `itemsPath` 를 뺍니다. `titlePaths`, `summaryPaths`, `authorPaths` 는 후보 경로 배열이고, 차례대로 처음 나오는 비어 있지 않은 값을 씁니다. 예: `["title", "name"]`.
- 완전한 웹 주소가 이미 있으면 `{raw:url}` 을 씁니다. slug 만 있으면 `https://example.com/posts/{slug}` 처럼 쓸 수 있습니다. `{필드경로}` 는 필드 값을 인코딩하고, `{raw:필드경로}` 는 그대로 넣습니다. JSON 목록은 상대 주소를 절대 주소로 자동으로 바꾸지 않으니, 템플릿이 완전한 HTTP(S) 주소를 만들어야 합니다.
- `summaryIsBody`: API 의 요약이 곧 전문이라고 확인했을 때 `true` 로 설정합니다. `summaryPaths` 로 얻은 텍스트를 본문으로 쓰고 원문 페이지를 다시 가져오지 않습니다.
- 날짜는 시간대가 붙은 ISO 문자열로 돌려주는 것이 좋습니다. `2026-09-30 17:43:58` 처럼 시간대가 없는 시각은 웹 목록과 똑같이 `publishedAtUtcOffset` 으로 읽습니다(기본 `+08:00`). 숫자 타임스탬프는 `publishedAtUnit: "epoch_s"`(초) 또는 `"epoch_ms"`(밀리초)를 설정하고, `20261001` 같은 날짜는 `"yyyymmdd"` 를 설정합니다.
- 제목이 없거나 링크를 만들 수 없는 항목은 건너뜁니다. 비어 있지 않은 배열이 하나도 매핑되지 않으면 `no items mapped (check title/url paths)` 오류가 납니다. 경로가 배열이 아니면 `items path did not resolve to an array` 오류가 납니다.

### HTML/JSON 예시를 로컬에서 돌려 보기

저장소에는 지어낸 예시 두 개가 있습니다. [news.html](../../../docs/examples/sources/news.html)과 [news.json](../../../docs/examples/sources/news.json)이고, 각각 뉴스가 두 개씩 들어 있습니다. 선택자와 필드 매핑을 맞춰 보는 용도이고, 운영용 출처가 아닙니다. 예시 기사 링크에는 본문이 없습니다.

저장소 루트에서 Node.js 24.11 이상으로 아래 명령을 실행합니다. 서버는 이 컴퓨터에서만 듣고, 이 두 파일만 내줍니다. `Ctrl+C` 로 멈춥니다.

```bash
node --input-type=module -e '
import http from "node:http";
import { readFileSync } from "node:fs";
const files = {
  "/news.html": ["text/html; charset=utf-8", readFileSync("docs/examples/sources/news.html")],
  "/news.json": ["application/json", readFileSync("docs/examples/sources/news.json")]
};
http.createServer((req, res) => {
  const file = files[req.url];
  res.writeHead(file ? 200 : 404, { "content-type": file ? file[0] : "text/plain" });
  res.end(file ? file[1] : "Not found");
}).listen(8787, "127.0.0.1");'
```

같은 컴퓨터에서 [Docker 를 쓰지 않는 배포 방식](deploy.md#docker-없이)대로 데이터베이스를 준비하고, `npm run dev:api`, `npm run dev:web` 으로 개발용 API 와 웹을 돌립니다. 수집, 모델, Feishu, IndexNow 스위치는 꺼 두고 worker 는 시작하지 않습니다. 이번 로컬 예시에 한해 개발용 API 프로세스에 `ALLOW_PRIVATE_NETWORK_FETCH=true` 를 설정하고 다시 시작합니다. 기본으로는 내부망 주소를 가져오지 못하게 막혀 있고, 운영 환경에서는 이 설정을 켜지 못합니다. 확인이 끝나면 지웁니다. API 가 컨테이너나 다른 서버에 있으면 `127.0.0.1` 은 그쪽 자신을 가리키므로, 이 명령의 주소를 그 배포에 바로 쓸 수 없습니다.

`web_list`, `json_list` 를 각각 골라 설정을 붙여 넣고 "미리 수집"을 누릅니다. 출처를 만들 필요는 없습니다.

```json
{
  "url": "http://127.0.0.1:8787/news.html",
  "parseMode": "html",
  "itemSelector": ".news-list > .news-item",
  "linkSelector": "h2 a",
  "titleSelector": "h2 a",
  "publishedAtSelector": "time",
  "allowUrlPrefixes": ["http://127.0.0.1:8787/posts/"]
}
```

```json
{
  "url": "http://127.0.0.1:8787/news.json",
  "mode": "json_api",
  "itemsPath": "data.items",
  "titlePaths": ["title"],
  "urlTemplate": "http://127.0.0.1:8787/posts/{id}",
  "summaryPaths": ["summary"],
  "publishedAtPath": "published_at",
  "externalIdPath": "id"
}
```

두 번 모두 **2개**가 나와야 하고, 차례대로 아래 표와 같습니다. JSON 예시는 해당 요약도 보여 주고, HTML 예시는 요약 추출을 설정하지 않았습니다. 미리 보기 API 의 날짜는 UTC 이고, 관리자 화면은 `+08:00` 기준으로 09:00 과 10:00 으로 보여 줍니다.

| 제목 | 원문 링크 | 미리 보기 API 의 publishedAt |
|---|---|---|
| 第一条示例新闻 | `http://127.0.0.1:8787/posts/first` | `2026-10-01T01:00:00.000Z` |
| 第二条示例新闻 | `http://127.0.0.1:8787/posts/second` | `2026-10-01T02:00:00.000Z` |

비교해 보려면 HTML 의 `itemSelector` 를 잠시 `.news-list` 로 바꿔 봅니다. 첫 번째 것만 나옵니다. `.news-list > .news-item` 으로 되돌리면 다시 두 개가 나옵니다. 이것이 "목록 컨테이너"와 "뉴스 하나하나"의 차이입니다.

실제 웹페이지를 가져올 때는 먼저 원래 HTTP 응답에 뉴스 노드가 있는지 봅니다. 일반 HTML 모드는 JavaScript 를 실행하지 않습니다. 브라우저에서는 보이지만 응답에는 없는 내용은 CSS 선택자를 바꾼다고 생기지 않습니다. RSS 나 JSON API 를 먼저 찾고, 필요하면 Jina 나 직접 관리하는 외부 수집을 설정합니다. `no items matched (html)` 은 선택자가 맞지 않거나, `href` 나 제목이 없거나, 링크가 접두어 규칙에 걸러져서 날 수도 있습니다. 수집기를 바꾸기 전에 응답과 설정부터 맞춰 봅니다.

### x_search

이 출처는 SocialData 검색을 씁니다. X 개인 페이지 URL 을 웹 목록에 넣는 방식이 아닙니다. `https://x.com/SomeAccount` 라면 사용자 이름 `SomeAccount` 만 쓰고, `@` 나 URL 전체는 넣지 않습니다.

```json
{ "query": "from:SomeAccount -filter:replies", "searchType": "Latest" }
```

`SomeAccount` 는 자리 표시용 사용자 이름이니 지켜볼 실제 계정으로 바꿉니다. `-filter:replies` 는 답글을 뺍니다. `Latest` 는 최신 내용 순으로 찾습니다.

백엔드 실행 환경의 `.env` 에 `SOCIALDATA_API_KEY` 를 설정하고, API(미리 보기)와 worker(정기 수집)를 다시 시작하면 적용됩니다. 키를 출처 JSON 에 쓰거나 저장소에 커밋하지 않습니다. 먼저 관리자 화면 "설정 → 유료 요청 한도"에서 SocialData 한도를 확인한 뒤 필요할 때 미리 봅니다. 키를 설정하지 않으면 `SOCIALDATA_API_KEY is not configured` 오류가 납니다. 서비스가 요청을 거부하거나 예산 차단기가 내려가면 관리자 화면의 오류 원인을 봅니다. 미리 보기는 유료 요청이 될 수 있습니다. 이 문서는 실제 서비스로 확인하라고 요구하지 않으며, 결과는 계정과 그때 서비스가 돌려준 값에 달려 있습니다.

운영 환경 자동 수집에서는 일반 계정들을 자동으로 한 번의 검색으로 합쳐(한 번에 최대 스무 개 남짓) 요청 수를 아낍니다. 출처 하나를 수동으로 미리 보는 것은 합친 수집이 아닙니다.

### mp_account

```json
{ "ghid": "gh_xxxxxxxx", "nickname": "公众号名称" }
```

공식계정마다 가져오기 간격에 따라 한 번씩 확인하고(목록 조회는 건당 과금), 새 글의 본문도 함께 받아 옵니다.

백엔드 `.env` 에 `DAJIALA_KEY` 를 설정해야 하고, `ghid` 는 공식계정의 원래 ID 로 바꿉니다. 설정 필드는 위의 `ghid` / `nickname` 을 쓰고, `biz` / `name` 으로 쓰지 않습니다. 지금 `mp_account` 는 "미리 수집"을 지원하지 않습니다. `external` 도 시험 삼아 가져오기를 지원하지 않으니, 아래 푸시 API 로 연결합니다.

## 등급, 참여 방식, 전문

- **등급** `tier`: `T1` 공식 1차(공식 사이트, 공식 블로그, 기관), `T1_5` 공식 계정과 준공식 창작자, `T2` 매체와 개인, `EXCLUDE_MP` 엄선에 참여하지 않음. 엄선 문턱은 등급마다 다릅니다(`industry/selection.ts`).
- **참여 방식** `participation_mode`: `editorial` 은 엄선과 전체 소식에 들어갑니다. `hot_signal` 은 따로 보여 주지 않고 "다들 무엇을 이야기하는지" 보여 주는 열기 증거로만 씁니다. `isolated` 는 어떤 공개 페이지에도 들어가지 않습니다.
- **1차**: `T1` 만 1차로 칩니다. 따로 설정하지 않습니다. 같은 뉴스를 여러 글이 다루면 대표 보도는 1차를 먼저 고르고, 이슈 페이지도 1차 보도를 먼저 보여 줍니다.
- **발행처**(선택, `config` 에 씁니다):
  - `publisherUrlPrefixes`: `T1` 출처 자기 기사 웹 주소의 접두어입니다. 예: `["https://example.com/blog/"]`. 다른 출처(모음 사이트, 퍼 나른 글)가 가져온 이 주소의 기사는, 공식 출처 하나로만 특정할 수 있으면 그 출처 이름으로 옮겨 기록합니다. 웹 목록 출처에서 쓰지 않으면 자기 목록이 있는 경로를 씁니다(이 글도 그 목록에 나온 적이 있어야 합니다).
  - `publisherRole`: `T1_5` 계정의 신분입니다. `organization`(기관 공식 계정) 또는 `person`(공식 인물)입니다. 출처의 `owner_entity_id`(`industry/taxonomy.ts` 의 `ENTITIES` id)도 채우면, 이 계정이 올린 글 중 주체가 바로 이 회사인 뉴스를 대표 보도로 쓸 수 있습니다(`T1` 다음 순서).
- **전문**: `site_fulltext` 는 사이트 안에서 전문을 보여 줄 수 있는지, `syndicate_fulltext` 는 전문 RSS 에 본문을 실을 수 있는지 정합니다. 둘 다 **기본은 꺼짐**이고, 요약과 원문 링크만 보여 줍니다. 출처가 분명히 허락할 때만 켭니다. 위챗 공식계정, 유료 장벽 안의 내용은 기술적으로 가져올 수 있다고 해서 전문을 보여 주지 않습니다.

## 가져오기 빈도

출처마다 자기 가져오기 간격이 있습니다. 매일 04:20 에 최근 7일 산출량을 보고 자동으로 조정합니다. 많이 나오는 곳일수록 자주 가져오고, 가장 짧게는 15분입니다(Jina 로 읽는 웹 목록은 가장 짧게 60분). 가장 길게는 일반 출처 60분, X 계정과 Jina 로 읽는 웹 목록 120분, 열기 증거로만 쓰는 곳 180분입니다. 합친 검색으로 묶인 X 계정은 합친 뒤의 박자를 따릅니다. 엄선에 들어가는 계정은 30분에 한 번, 열기 증거로만 쓰는 계정은 1시간에 한 번입니다.

가져오기에 실패하면 위치를 앞으로 옮기지 않고 다음에 같은 자리부터 이어 갑니다. 계속 실패하는 출처는 관리자 화면에 빨갛게 표시되고, 매주 월요일 운영 그룹 채팅에 출처 주간 보고를 보냅니다(Feishu 내부 그룹을 설정했을 때).

"7일 동안 새 내용 없음"은 고정된 기간이 아니라 **출처 자신의 박자**로 판단합니다. 일간·주간 브리핑에서는 두 부류로 나눕니다. **자기 업데이트 박자를 넘긴** 출처를 앞에 두니, 먼저 원래 사이트와 맞춰 봅니다(최근 90일의 **산출일**을 "날" 단위로 중복을 없애고, 이웃한 두 날의 간격의 중앙값을 그 출처의 박자로 삼습니다. 이런 날이 적어도 4개는 있어야 박자가 있다고 보고, 조용한 기간이 중앙 간격의 4배를 넘어야 넘긴 것으로 봅니다). 산출일은 그 내용의 발행 시각을 쓰고, 페이지에 시각이 없으면 우리가 그것을 발견한 날을 씁니다. **첫 불러오기 한 번은 하루로 칩니다**. 첫 불러오기는 한 번의 전달이라, 발행 시각이 얼마나 멀리 거슬러 올라가든 여러 번 산출한 것으로 치지 않습니다(그러지 않으면 한 번도 산출하지 않은 출처가 아주 꼬박꼬박 내는 것처럼 보이고, 여러 달에 걸친 첫 불러오기가 중앙 간격을 늘려 이미 조용해진 출처를 숨기게 됩니다). 기간은 이 90일 안의 산출일만 셉니다. 더 오래된 기록은 지금 얼마나 자주 내는지 말해 주지 못합니다. 발견 시각과 발행 시각은 어느 쪽이 먼저라고 정해져 있지 않아서, 둘 중 하나라도 기간 안에 있으면 읽고, 산출일을 다시 기간에 맞춰 자릅니다. **박자를 판단할 수 없는 출처도 목록에 올리지만** 고장으로 보지는 않습니다. 두 경우가 있습니다. 기간 안에 비교할 산출이 없는 경우(산출한 적은 있지만 모두 기간 밖)와, 내용을 한 번도 받은 적이 없는 경우(이것은 수집 문제)입니다. 자기 박자 안에 있는 출처는 더 이상 목록에 올리지 않습니다. 가져오기 간격 `interval_minutes` 는 판단에 쓰지 않습니다. 이것은 우리가 얼마나 자주 보는지이지, 출처가 얼마나 자주 내는지가 아닙니다.

## 규칙: 옛 글이 화면을 덮지 않게

처음 발견했을 때 원문이 이미 발행된 지 48시간이 넘은 자료, 새 출처를 처음 불러올 때 들어온 기존 항목, 되채우기로 표시된 푸시는 모두 원문 시각으로 보관합니다. "오늘"에 들어가지 않고 푸시도 하지 않습니다. 믿을 만한 발행 시각이 없는 자료는 일단 공개하지 않고(공개 목록, 엄선, 보고서, 핫이슈, 푸시에 넣지 않습니다), 원래 출처나 원문 페이지에서 날짜를 읽은 뒤 새것인지 옛것인지 판단합니다. 이 규칙은 모든 입구가 함께 씁니다. 한 번에 옛 내용을 불러와 화면을 덮는 일을 막습니다.

새 출처를 처음 불러올 때는 목록 앞쪽의 `_aihot.initialBackfillLimit` 개(기본 30), `_aihot.initialBackfillMonths` 개월 안(기본 12)의 항목만 가져옵니다. 그 뒤 가져오기는 발행 시각이 출처를 처음 불러오기 48시간 전 이후인 항목만 받습니다. 목록에 있는 더 오래된 기존 항목은 더 들어오지 않고, 구독 전체 보관분에 돈을 쓰지 않습니다. 첫 불러오기 뒤에 발행된 항목은 긴 목록의 몇 번째에 있든 받습니다. 목록에 발행 시각이 없는 항목도 받고, 위 규칙대로 날짜를 읽을 때까지 기다렸다 판단합니다. X 계정은 가져오기 위치부터 뒤로 읽으므로 이 제한을 받지 않습니다.

정해 둔 시각 이후부터만 지켜보고 싶으면 RSS, 웹 목록, JSON 설정에 `publishedAfter` 를 설정합니다. 예: `"2026-10-01T00:00:00.000Z"`. 완전한 UTC 시각이어야 하고 밀리초는 빼도 됩니다. 미리 보기, 첫 수집, 이후 수집 모두 이 시각보다 **엄격하게 늦고** 발행일을 믿을 수 있는 항목만 받습니다. 날짜를 모르는 항목도 뺍니다. 시작일 당일의 한 페이지짜리 업데이트 절이 계속 같은 발행일을 쓰면, 그 뒤에 덧붙인 내용도 들어오지 않습니다. 시작 시각을 고를 때 이 제한을 생각해야 합니다.

## 외부 푸시 API

직접 스크립트로 가져온 내용을 사이트에 넣을 수 있습니다. 일반 수집과 똑같이 중복 판단, 엄선, 묶기를 거칩니다.

```
POST /api/ingest/items
Authorization: Bearer <INGEST_TOKEN>
Content-Type: application/json

{
  "sourceId": "my-crawler",
  "sourceName": "我的抓取脚本",
  "items": [
    { "title": "必填", "url": "必填", "publishedAt": "2026-10-01T08:00:00+08:00", "author": "可选" }
  ]
}
```

- `INGEST_TOKEN` 은 `.env` 에서 설정하고, 16자 이상이어야 합니다. 설정하지 않으면 API 는 언제나 401 을 돌려줍니다.
- 한 번에 최대 50개이고, 넘으면 413 을 돌려줍니다. 클라이언트마다 1분에 몇 번 푸시할 수 있는지는 `INGEST_RATE_LIMIT` 가 정합니다. `docker compose` 는 기본 10이고, 넘으면 429(`Retry-After: 60` 포함)를 돌려줍니다. Docker 를 쓰지 않으면 기본은 제한 없음이니, 앞단에 속도 제한을 하는 리버스 프록시가 없다면 `.env` 에 설정합니다. 0으로 두면 제한 없음입니다.
- `{"ok": true, "created": <새로-만든-건수>}` 를 돌려줍니다. JSON 객체가 아닌 항목, 제목이나 웹 주소가 없는 항목은 건너뛰고, 한 요청 안에서 웹 주소가 겹치면 첫 번째만 씁니다.
- `sourceId` 가 없으면 `external` 출처를 자동으로 하나 만들고, 기본으로는 공개 페이지에 들어가지 않습니다. 관리자 화면에서 참여 방식을 `editorial` 로 바꿔야 사이트에 나옵니다.
- 관리자 화면에서 출처를 멈추면 푸시 API 는 409 를 돌려주고 새 글을 받지 않습니다. 출처를 다시 켜면 다시 푸시할 수 있습니다.
- 항목의 `raw._aihot.backfill` 이 `true` 이면 옛 기록 되채우기로 처리합니다("오늘"에 들어가지 않고 푸시하지 않습니다).
